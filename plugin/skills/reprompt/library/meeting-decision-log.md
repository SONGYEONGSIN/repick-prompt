## 본문

```
당신은 회의에서 나온 결정을 나중에도 정확히 되짚을 수 있게 기록하는 조직의 기록 관리자입니다. 당신의 목표는 매끄러운 요약이 아니라, "누가·언제·무엇을 근거로 이렇게 결정했는가"를 실제로 추적할 수 있는 원장이며, 확실하지 않은 결정은 짐작으로 채우지 않고 확인할 수 있는 사람에게 되돌려 보내는 것입니다.

아래 회의 원문을 바탕으로 결정 원장을 작성해주세요.
- 회의 주제/목적: {{meeting_topic}}
- 참석자와 역할: {{attendees}}
- 회의 원문 기록: {{content}}
- 이 기록을 작성하는 사람: {{tracker}}
- 불확실한 결정을 확인받아야 하는 기한: {{verification_deadline}}

요구사항:
1. 결정마다 독립된 카드로 분리해 "결정 내용 / 담당자 / 합의된 시점(또는 마감) / 근거 발언(화자명 + 원문 인용) / 확인 상태"를 적어주세요. 확인 상태는 반드시 "확정"(원문에 담당자·시점·내용이 모두 명확) / "조건부 확정"(원문에 조건이나 전제가 붙어 있었음) / "확인 필요"(담당자·시점·내용 중 하나 이상이 원문에서 불명확) 셋 중 하나로 판정해주세요. 상태를 나누지 않으면 나중에 원장을 보는 사람이 어떤 결정을 그대로 믿고 움직여도 되는지 스스로 다시 판단해야 하기 때문입니다.
2. 근거 발언은 원문 표현을 그대로 짧게 인용해주세요. 인용을 요구하면 AI가 없는 발언을 지어내기 어려워지고, 확인 상태 판정의 근거를 읽는 사람이 직접 검증할 수 있기 때문입니다.
3. "확인 필요"로 판정한 결정은 절대 짐작으로 채우지 마세요. 대신 참석자 목록 중 그 결정과 가장 관련 있는 사람을 지목해 "누구에게, 무엇을, 왜 확인해야 하는지"를 한 줄씩 별도의 확인 요청 목록에 적어주세요. 회의록에 없는 내용을 그럴듯하게 채우면 읽는 사람은 그것이 실제 결정인지 기록자의 짐작인지 구분할 수 없고, 짐작이 결정으로 굳어지면 실제로 합의한 적 없는 일에 책임을 지는 사람이 생기기 때문입니다.
4. 확정된 결정과 논의만 됐을 뿐 아직 정해지지 않은 사항을 분리해주세요. 회의록 사고의 대부분은 "얘기만 나온 것"을 "정해진 것"으로 오해하는 데서 나오기 때문입니다.
5. 회의 중 언급된 리스크나 우려사항이 있으면 결정 카드와 분리해 별도로 표시해주세요. 흘려 언급된 우려는 결정 카드에 묻히면 놓쳐졌다가 나중에 문제로 터지기 때문입니다.
6. 문장은 간결하게 쓰고, 원문에 없는 배경 설명이나 해석을 덧붙이지 마세요. 해석이 섞이면 이 원장이 "무엇이 있었는가"의 사실 기록인지 기록자의 의견인지 나중에 구분할 수 없게 되기 때문입니다.

출력 형식:
- 한 줄 요약 (확정 N건 · 조건부 N건 · 확인 필요 N건)
- 결정 원장 (각 카드: 결정 내용 · 담당자 · 시점 · 근거 인용 · 확인 상태)
- 확인 요청 목록 (각 줄: 확인 대상자 · 확인할 질문 · 관련 결정 · 기한)
- 미결 이슈
- 리스크/주의사항
```

## 해부

### 역할

> 당신의 목표는 매끄러운 요약이 아니라 … 실제로 추적할 수 있는 원장이며, 확실하지 않은 결정은 짐작으로 채우지 않고 확인할 수 있는 사람에게 되돌려 보내는 것입니다.

역할 정의 자체에 "불확실한 것은 스스로 판단하지 말고 되돌려 보낸다"는 태도를 못박습니다. AI가 완결된 결과물을 내놓아야 한다는 암묵적 압박이 빈틈을 메우려는 유혹을 만든다면, 이 역할은 애초에 "완결"의 기준을 결정 원장의 형식적 완성이 아니라 정확한 확인 상태 판정으로 재정의합니다.

### 확인 상태 3분류 요구사항

> 확인 상태는 반드시 "확정" / "조건부 확정" / "확인 필요" 셋 중 하나로 판정해주세요.

이 원칙이 도메인 본질을 정면으로 겨냥합니다. 결정이냐 아니냐의 이분법(meeting-summary 시드의 결정/미결 분리)을 한 단계 더 쪼개, "결정처럼 보이지만 담당자나 시점이 불명확한" 회색지대를 별도 판정으로 강제 노출합니다. 오귀속은 대개 이 회색지대가 조용히 "확정"으로 승격될 때 일어납니다.

### 확인 요청 라우팅 (자기검증도 원천 차단도 아닌 제3의 대응)

> "확인 필요"로 판정한 결정은 절대 짐작으로 채우지 마세요. 대신 참석자 목록 중 그 결정과 가장 관련 있는 사람을 지목해 "누구에게, 무엇을, 왜 확인해야 하는지"를 한 줄씩 별도의 확인 요청 목록에 적어주세요.

이번 라운드의 방향 가설이 다루는 두 대응(a: AI가 그냥 다루지 않는다 / b: AI가 스스로 점검해 채운다)과 다른 세 번째 경로입니다. 불확실성을 AI 내부에서 해소하려 하지 않고, 실제로 답을 아는 사람(회의 참석자)에게 명시적인 다음 행동으로 넘깁니다. 확인 요청이 실행되면 원장 자체가 갱신될 수 있는 살아있는 문서가 됩니다.

### 출력 형식의 정량 집계

> 한 줄 요약 (확정 N건 · 조건부 N건 · 확인 필요 N건)

첫 줄에 상태별 건수를 집계해 "이 회의록에서 그대로 믿고 움직여도 되는 결정이 몇 개인지"를 3초 안에 파악하게 합니다. 결정 요청을 문서 상단에 고정하는 기존 DNA 원칙(R5)의 변형으로, 여기서는 요청 대신 신뢰도 집계가 상단에 옵니다.

## 팁

- "확인 필요" 항목에 대한 답을 받으면, 그 답변을 이 대화에 붙이고 "이 답변으로 확인 필요였던 항목들의 확인 상태를 갱신해줘"라고 요청하면 원장이 최신 상태로 업데이트됩니다.
- 같은 프로젝트가 여러 번 회의하면, 이전 회의의 결정 원장을 이번 회의 원문 앞에 붙여넣고 "지난 회의의 확인 필요 항목 중 이번 회의에서 확정된 게 있으면 표시해줘"라고 하면 확인 요청이 실제로 해소됐는지까지 추적할 수 있습니다.
