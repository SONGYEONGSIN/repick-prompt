# 코드 리뷰

씨앗 — 사용자 제공 검증 프롬프트

## 필드

```json
[
  {
    "key": "purpose",
    "label": "변경 목적",
    "type": "text",
    "help": "이 코드가 무엇을 하려는 변경인지. 리뷰의 기준점이 됩니다.",
    "placeholder": "예: 로그인 실패 시 재시도 로직 추가"
  },
  {
    "key": "code",
    "label": "관련 파일/코드",
    "type": "textarea",
    "placeholder": "리뷰받을 코드 또는 diff를 붙여넣기"
  },
  {
    "key": "concerns",
    "label": "우려하는 부분",
    "type": "select",
    "options": [
      "성능",
      "안정성",
      "보안",
      "테스트",
      "없음"
    ]
  },
  {
    "key": "context",
    "label": "프로젝트 맥락",
    "type": "select",
    "options": [
      "웹앱",
      "API",
      "데이터 파이프라인"
    ],
    "help": "같은 코드도 맥락에 따라 위험도가 다릅니다."
  }
]
```

## 본문

```
당신은 시니어 소프트웨어 엔지니어이자 코드 리뷰어입니다.

아래 코드 변경을 리뷰해주세요.
- 변경 목적: {{purpose}}
- 관련 파일/코드: {{code}}
- 우려하는 부분: {{concerns}}
- 프로젝트 맥락: {{context}}

리뷰 기준:
1. 스타일보다 실제 버그 가능성과 회귀 위험을 우선해서 봐주세요. 리뷰의 목적은 배포 후 터질 문제를 미리 잡는 것이라, 스타일 지적에 매몰되면 정작 위험한 결함을 놓치기 때문입니다.
2. 문제가 있다면 왜 문제인지 구체적으로 설명해주세요. 근거 없는 지적은 작성자가 납득하지 못해 안 고치거나 잘못 고치고, 이유가 있어야 같은 실수를 다시 안 하기 때문입니다.
3. 심각도는 높음/중간/낮음으로 나눠주세요. 모든 지적이 같은 무게로 나열되면 무엇을 머지 전에 반드시 고쳐야 하는지 판단할 수 없기 때문입니다.
4. 테스트가 부족하면 어떤 테스트가 필요한지 제안해주세요. 지금 통과해도 테스트 없는 코드는 다음 변경에서 조용히 깨지므로, 회귀를 막을 테스트를 함께 짚어야 하기 때문입니다.
5. 큰 문제가 없다면 잔여 리스크와 확인 포인트를 남겨주세요. '문제 없음'만으로는 리뷰어가 어디까지 봤는지 알 수 없어, 남은 위험과 확인 포인트가 있어야 안심하고 머지할 수 있기 때문입니다.

출력 형식:
- 요약 한 줄
- 주요 이슈 목록 (심각도 포함)
- 테스트/검증 제안
- 머지 전 체크포인트
```

## 해부

### 역할

> 시니어 소프트웨어 엔지니어이자 코드 리뷰어

'시니어'와 '리뷰어'를 함께 지정하면 코드를 다시 짜주는 게 아니라 위험을 짚는 관점으로 답합니다.

### 맥락

> 변경 목적 / 우려 부분 / 프로젝트 맥락

변경 목적 없이 코드만 주면 AI는 의도를 추측합니다. 목적을 주면 '의도 대비 구현'을 검증할 수 있습니다.

### 리뷰 기준

> 스타일보다 버그·회귀 우선 / 심각도 분류

기준이 없으면 AI 리뷰는 사소한 스타일 지적으로 흘러갑니다. 우선순위를 명시해 진짜 위험에 집중시킵니다.

### 출력 형식

> 요약 → 이슈(심각도) → 테스트 제안 → 머지 전 체크포인트

머지 전 체크포인트로 끝나 리뷰가 실제 배포 판단으로 이어집니다.

## 팁

- 코드가 길면 변경된 부분(diff)만 넣고 "전체 맥락이 필요하면 질문해줘"라고 하세요.
- 리뷰 결과 중 이해 안 되는 지적은 "3번 이슈를 실제 시나리오 예시로 설명해줘"라고 파고드세요.
