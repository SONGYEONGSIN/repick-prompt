# 고객 인터뷰 인사이트 분석

씨앗 — 사용자 제공 검증 프롬프트

## 필드

```json
[
  {
    "key": "product",
    "label": "제품/서비스명",
    "type": "text",
    "placeholder": "예: 리픽 — AI 중고거래 매칭"
  },
  {
    "key": "purpose",
    "label": "인터뷰 목적",
    "type": "text",
    "placeholder": "예: 온보딩 이탈 원인 파악"
  },
  {
    "key": "target",
    "label": "대상 고객",
    "type": "text",
    "placeholder": "예: 가입 후 첫 구매 전 이탈한 사용자 5명"
  },
  {
    "key": "transcript",
    "label": "인터뷰 기록",
    "type": "textarea",
    "help": "여러 명이면 인터뷰이별로 구분선(---)을 넣어 붙여넣으세요.",
    "placeholder": "인터뷰 내용 전체를 붙여넣기"
  }
]
```

## 본문

```
당신은 PM과 UX 리서처를 돕는 분석가입니다.

아래 고객 인터뷰 내용을 바탕으로 핵심 인사이트를 정리해주세요.
- 제품/서비스명: {{product}}
- 인터뷰 목적: {{purpose}}
- 대상 고객: {{target}}
- 인터뷰 기록: {{transcript}}

분석 기준:
1. 고객이 직접 말한 불편과 암묵적으로 드러난 불편을 구분해주세요. 고객은 진짜 문제를 스스로 다 말로 꺼내지 못하고, 말 뒤에 숨은 불편에 더 큰 기회가 있기 때문입니다.
2. 반복적으로 등장하는 패턴을 찾아 빈도와 함께 정리해주세요. 한 명의 강한 의견은 예외일 수 있지만, 여러 명이 반복하는 것은 실제 우선순위 신호이기 때문입니다.
3. 구매/사용을 촉진하는 요인과 방해하는 요인을 나눠주세요. 무엇을 늘리고 무엇을 없앨지가 갈려야, 분석이 '흥미로운 발견'에서 끝나지 않고 행동으로 이어지기 때문입니다.
4. 제품팀이 바로 검토할 수 있는 개선 기회를 우선순위 순으로 제안해주세요. 인터뷰에서 나온 기회는 늘 많아서, 우선순위가 없으면 제품팀이 무엇부터 손댈지 정하지 못하기 때문입니다.
5. 가능한 경우 근거가 되는 원문 표현을 짧게 인용해주세요. 인용을 요구하면 AI가 없는 내용을 지어내기 어려워지고, 근거가 붙은 인사이트라야 팀을 설득할 수 있기 때문입니다.

출력 형식:
- 핵심 인사이트 요약
- 주요 Pain Point
- 동기/트리거
- 반복 패턴
- 개선 기회 우선순위
- 제품팀이 다음 주에 바로 확인할 실험 아이디어 3개
```

## 해부

### 역할

> PM과 UX 리서처를 돕는 분석가

결과를 소비할 사람(PM·리서처)을 역할에 박아두면, 그들이 쓰는 프레임(Pain Point, 트리거)으로 정리됩니다.

### 맥락

> 제품명 / 인터뷰 목적 / 대상 / 원문

목적('온보딩 이탈 원인')이 분석의 렌즈가 됩니다. 목적 없이 넣으면 뻔한 요약만 나옵니다.

### 분석 기준

> 직접 발화 vs 암묵적 불편 구분 / 빈도 / 원문 인용

인용을 요구하면 AI가 지어내기 어려워집니다. 근거 요구는 환각을 줄이는 가장 쉬운 장치입니다.

### 출력 형식

> 인사이트 → Pain Point → 패턴 → 우선순위 → 실험 3개

분석이 '흥미로운 발견'에서 끝나지 않고 다음 주 실험으로 착지합니다.

## 팁

- 인용된 원문이 실제 기록에 있는지 한 번 검수하세요. 근거 확인은 사람의 몫입니다.
- "이 결과를 노션에 붙일 표 형태로 다시 정리해줘"라고 하면 공유 문서화가 빨라집니다.
