# DOMAIN — 긴 자료 핵심 요약 (R27)

## 1. 본질 리스크

이 도메인 결과물이 실패하는 1순위 원인은 **누락(omission)**이다 — 원문이 길기 때문에 AI가 눈에 띄는 일부(도입부·결론부·강한 주장)에만 집중하고 중간에 묻힌 수치·반례·소수 의견을 놓친다. `meeting-summary`(R-seed)는 "정리 기준"에서 결정/미결 분리·리스크 별도 표시로 이 리스크의 일부(회의록 한정)를 이미 막고 있지만, 회의록보다 구조가 불규칙한 자료(보고서·논문·긴 스레드·기사)는 섹션 경계 자체가 명시적이지 않아 위험이 더 크다. 2차 리스크는 **목적 렌즈 부재로 인한 밋밋한 요약**("요약이 요약이 아니라 축약된 재진술")이다 — 같은 자료도 "투자 여부 판단용"과 "팀 공유용"은 다른 문장이 핵심이어야 한다.

## 2. 본질 루프

**"만들면 끝"에 가깝다.** 마케팅 이메일·광고처럼 발송 후 성과를 측정·반복하는 구조가 아니다 — 요약본은 그 자리에서 소비되고 끝난다. 다만 회의록 요약(R-seed)처럼 "너무 길면 나눠 넣고 마지막에 합쳐줘"라는 팁이 있듯, 원문이 모델 처리 한도를 넘는 경우의 **분할 요약→통합** 루프가 있을 수 있으나 이는 실험 문법(가설-지표-판정)과는 다른 종류의 반복이라 방향 풀에 실험 카드형을 필수로 넣을 근거는 약하다.

## 3. 결과물의 소비 방식

**정독을 대체하려고 요약을 소비한다** — "원문을 읽을 시간이 없는" 사람이 3분 내로 스캔하고, 필요하면 요약이 가리키는 원문 특정 지점으로 되돌아간다. 채널은 다양하다(보고서 PDF, 논문, 슬랙 긴 스레드, 뉴스 기사). meeting-summary의 "역피라미드"(바쁘면 첫 줄만, 실무자는 액션 표만) 소비 패턴과 유사하되, 이 도메인은 액션 아이템이 아니라 **핵심 주장·근거·수치**가 스캔 대상이다.

## 4. 유사 라운드 전례

- **meeting-summary (seed, summary 카테고리 유일)** — "결정 vs 미결 분리", "리스크 별도 표시"가 이 도메인의 "다뤄진 것 vs 다뤄지지 않은 것" 분리와 구조적으로 가장 가깝다.
- **R16 business-email-reply** — "요청 개수를 세고 대조 확인한 뒤 최종본만 출력, 점검 과정은 본문에 노출 금지"라는 완전성 자가검증 요구사항이 이번 라운드의 방향 가설(자가점검 로그)과 표면적으로 겹친다. R16은 애매 판정(정량적 완전성 대조 vs 정성적 저항 지점 비평, 축 통합 여부 미정)으로 남아 있다.
- **R26 research-questions** — 방향 가설(요구사항 준수 인라인 자가점검 로그, 본문 노출 vs 부속 분리)이 이번 라운드가 재검하는 대상. R26에서는 편향 차단 축은 이겼으나 바로사용가능성이 깎여 종합 패배.

## 5. 방향 풀 추천

라운드당 후보 3개, 하나는 backlog 방향 가설(자가점검 로그 통제쌍)을 소비해야 하므로 다음과 같이 설계한다:

- **a — 결합형 표준 + 자가점검 로그 본문 노출**: 원문 인용 근거 + 목적 렌즈(purpose 필드) + BLUF(결론 우선) 구조를 내장한 베이스에, "커버리지 자가점검" 로그(원문 섹션별 반영 여부 판정)를 **본문 안에** 노출.
- **b — 결합형 표준 + 자가점검 로그 부속 분리** (a와 완전히 동일한 베이스, 로그 노출 위치만 다름): 같은 자가점검을 **본문 밖 부속 메모**로 분리해 실행. a/b는 로그 노출 위치 하나만 다른 순수 통제쌍이다.
- **c — 도메인 본질 정면 겨냥형(구조적 완전성 강제)**: 본질 리스크(누락)를 사후 점검(로그)이 아니라 **사전에 구조로 봉쇄** — 원문에서 목차/섹션을 먼저 추출해 섹션마다 최소 1문장씩 강제 배정하는 절차를 요구사항에 내장, 사후 자가점검이 없어도 처음부터 빠짐없이 훑게 만든다. a/b가 "사후 점검형"이라면 c는 "사전 구조 강제형" — 같은 리스크를 겨냥하는 다른 기제라 대조가 유의미하다.
