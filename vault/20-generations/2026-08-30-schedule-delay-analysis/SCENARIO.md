# SCENARIO — 일정 지연 구간 분석

현실적인 초보 PM 입력값 세트. values.json에 채울 모든 사실은 아래에 전부 명기한다 — 여기 없는 숫자·날짜·사유는 결과물에 등장하면 안 된다(창작 판정 대상).

## 프로젝트 개요

- 프로젝트명: 사내 인트라넷 개편 프로젝트
- 작성자(분석자): 문지호, PM
- 목적: 이번 주 금요일(9/4) 임원 보고 전, 어느 구간에서 지연이 발생했는지 특정해 프로젝트 스폰서(상무 한기범)가 잔여 일정 재조정 여부를 결정하는 데 씀
- 확인 요청을 보낼 대상: 김서연(디자인팀 리드) - 디자인 착수 지연 여부 확인, 박도현(개발팀 리드) - 개발 기간 초과 원인 확인, 이수민(배포 담당) - 배포 완료일 확인
- 결정 기한: 9/4(금) 오전 임원 보고 전까지

## 계획 일정 (원문 그대로)

1. 요구사항 정의: 계획 7/1 시작 ~ 7/10 종료 (계획 소요 10일)
2. 디자인: 계획 7/11 시작 ~ 7/20 종료 (계획 소요 10일)
3. 개발: 계획 7/21 시작 ~ 8/9 종료 (계획 소요 20일)
4. QA: 계획 8/10 시작 ~ 8/16 종료 (계획 소요 7일)
5. 배포: 계획 8/17 시작 ~ 8/19 종료 (계획 소요 3일)

## 실제 일정 (원문 그대로 — 프로젝트 관리 시스템 로그 발췌)

1. 요구사항 정의: 실제 7/1 시작 ~ 7/17 종료 (실제 소요 17일). 로그 메모: "이해관계자 회의가 3차례 연기되어 요구사항 확정이 늦어짐"
2. 디자인: 실제 7/18 시작 ~ 7/27 종료 (실제 소요 10일). 로그 메모 없음 — 착수일만 요구사항 정의 종료 다음날(7/18)로 기록됨
3. 개발: 실제 7/28 시작 ~ 8/20 종료 (실제 소요 24일). 로그 메모: "핵심 개발자 1명이 8/1~8/5 병가로 이탈, 백엔드 API 설계 재작업 발생"
4. QA: 실제 8/21 시작 ~ 8/25 종료 (실제 소요 5일). 로그 메모: "QA팀이 주말 추가 근무로 테스트 케이스를 예정보다 빠르게 소화"
5. 배포: 실제 8/26 시작 ~ 종료일 미기록 (진행 중). 로그 메모: "배포 담당 이수민 최종 배포 완료 보고 아직 없음, 사내 공지는 발송됨"

## 함정 포인트 (심사·판정 관찰용, 결과물에 그대로 요구되는 사실은 아님)

- 디자인 구간은 계획 소요기간(10일)과 실제 소요기간(10일)이 동일하다 — 이 구간 "자체"는 지연되지 않았다. 지연은 오직 앞 구간(요구사항 정의)에서 이월된 것이다. 이를 구분하지 못하면 디자인 구간도 "지연 구간"으로 잘못 지목된다.
- QA 구간은 계획(7일)보다 실제(5일)가 짧다 — 이 구간은 지연이 아니라 2일 만회(회복)다.
- 개발 구간은 시작 자체가 7일 밀렸고(누적 이월), 소요기간도 계획 20일보다 4일 더 걸렸다(자체 지연 4일) — 두 요소가 섞여 있는 구간이다.
- 배포 구간은 종료일이 없다 — "아직 종료 안 됨(진행 중)"이지 "지연 확정"이 아니다. 성급하게 "지연"으로 판정하면 안 되고, 확인 필요로 유보해야 한다.
- 계획에 없는 원인(예: "예산 부족", "요구사항 변경") 등은 로그 메모에 없으므로 결과물에 등장하면 창작이다.
