# SCENARIO — R46 데이터 이관 검증 보고서

> 동일 테스트 시나리오. values.json에 채울 모든 사실(수치·기한·부가 정보 포함)을 여기 빠짐없이 명기한다 — 심사자는 이 문서만 보고 결과물을 대조하므로, 여기 없는 사실이 결과물에 등장하면 창작으로 판정한다.

## 심사자가 대조에 쓸 사실 요약 (결과물 판정용, SCENARIO 밖 정보 아님)

- 위 10개 항목(원본 9건 + 대상 전용 1건) 외에 다른 사실은 존재하지 않는다. raw에 없는 이관 실패 원인(네트워크 오류·인코딩 깨짐 등)을 결과물이 새로 만들어 붙이면 창작이다.
- **일치(정상 변환 포함)**: ORD-88301, ORD-88302, ORD-88307 — 3건. (301·302는 선언된 변환 규칙만 적용됐고 값 자체는 동일, 307은 완전 무변화.)
- **변형 의심**: ORD-88303(상품명 공백 제거, 선언된 규칙 밖·비민감 필드), ORD-88304(이메일은 규칙 적용 정상이나 결제금액 15,000원 차이는 규칙 밖·민감 필드), ORD-88306(전화번호 끝자리 실제 변경, 하이픈 제거로 위장됐으나 규칙 밖·민감 필드) — 3건.
- **완전 유실**: ORD-88305(사유 언급 전혀 없음 — "원인 미상"), ORD-88308(구두 진술만 있고 서면 근거 없음 — "추정 정황"으로 표시, 정상 제외로 확정 처리하면 안 됨) — 2건.
- **확인 불가(재검증 필요)**: ORD-88309 — 대상 존재 여부 자체가 미확인. "완전 유실"로 단정하면 근거 없는 창작이다.
- **예상 밖 신규 출현**: ORD-88399 — 원본 어디에도 없는데 대상에만 존재. 사유는 QA의 구두 추측뿐이므로 "(추정 정황: …)"으로 표시, 확정 사유로 쓰면 안 된다.
- 검산: 원본 9건 = 일치 3 + 변형의심 3 + 완전유실 2 + 확인불가 1 (3+3+2+1=9). 신규출현 1건은 원본 9건과 별개 집계.
- 확인 요청 라우팅: ORD-88303·88304·88306은 실제로 값을 확인할 수 있는 사람(이관 스크립트 작성자 오지훈 또는 QA 박서연)에게, ORD-88305는 원인 파악이 가능한 오지훈에게, ORD-88308은 결제팀 유지수에게(구두 진술의 당사자), ORD-88309는 오지훈에게(재검증 담당), ORD-88399는 박서연에게(구두 추측의 당사자) 확인을 요청하는 것이 맞다. 컷오버 승인권자 강지원에게 개별 사유 확인을 요청하면 v1.27/v1.38이 지적한 라우팅 오류다.
