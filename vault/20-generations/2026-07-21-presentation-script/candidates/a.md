# 후보 a — 오프닝훅-본론-클로징 구조를 요구사항에 내장하고, 코치형 help로 초보자의 입력 품질을 끌어올리며, 청중 특성과 발표 자리 성격을 전용 빈칸으로 받는 결합형 표준

## fields

| key | label | type | optional | help | placeholder | options |
|-----|-------|------|----------|------|-------------|---------|
| topic | 발표 주제 | text | no | 무엇에 대한 발표인지 한 문장으로 적으세요. 주제가 모호하면 오프닝 훅부터 방향을 못 잡습니다. | 3분기 신규 결제 시스템 도입 제안 | |
| audience | 청중 특성 | textarea | no | 청중이 누구고, 이 주제에 대해 얼마나 알고 있고, 무엇에 관심 있는지 적으세요. 같은 내용도 청중의 배경지식과 관심사에 따라 설명 수준과 강조점이 완전히 달라집니다. | 임원 5명, 기술적 배경 없음, 비용과 리스크에 가장 민감하게 반응함 | |
| occasion | 발표 자리 성격 | text | no | 사내 보고인지, 세미나인지, 투자 피칭인지에 따라 격식과 증거 수준이 달라집니다. 발표 후 바로 이어지는 일정(질의응답, 결재 등)도 함께 적으면 클로징의 방향이 더 정확해집니다. | 임원 대상 분기 보고, 발표 후 바로 예산 승인 여부 결정 | |
| goal | 발표 목표 | text | no | 듣고 난 뒤 청중이 구체적으로 무엇을 해주길 바라는지 적으세요. 이게 클로징의 마지막 행동 요청 문장을 결정합니다. | 이번 분기 예산으로 새 결제 시스템 도입을 승인받기 | |
| duration | 발표 시간 | text | no | 실제로 소리 내어 말할 시간을 분 단위로 적으세요. 시간을 정하지 않으면 분량이 통제되지 않아, 리허설 때 앞부분은 자세히 뒷부분은 어물쩍 넘어가는 스크립트가 나옵니다. | 10분 (이후 질의응답 5분) | |
| key_content_raw | 핵심 내용과 근거 원본 메모 | textarea | no | 가장 중요한 칸입니다. 전달할 핵심 메시지와 그걸 뒷받침하는 실제 데이터·사례·근거를 날것 그대로 적으세요. 매끈한 문장일 필요 없습니다. 여기 없는 내용은 지어내지 않으므로, 자세히 적을수록 근거 있는 발표가 됩니다. | 핵심 메시지: 새 시스템 도입 시 결제 처리 시간 40% 단축. 근거: 지난달 파일럿 테스트에서 평균 3.2초→1.9초, 오류율 2%→0.4%. 도입 비용은 월 200만원 추가. | |
| tone | 톤 | select | yes | 발표 말투의 방향입니다. 목록에 없으면 원하는 톤을 직접 적어도 됩니다. 고민되면 비워두세요, 발표 자리 성격에 맞춰 무난하게 잡습니다. | 담백하고 데이터 중심 | ["담백하고 데이터 중심", "편안하고 스토리텔링 위주", "확신에 찬 설득형", "겸손하고 신중한"] |
| avoid_points | 피해야 할 표현·주의할 배경 | textarea | yes | 이 주제로 이전에 부정적 반응이 있었거나, 언급하면 안 되는 민감한 배경이 있다면 적으세요. 없으면 비워두세요. | 지난 분기 비슷한 제안이 "검토 부족"이라는 이유로 반려된 적 있음. "경쟁사" 대신 "유사 서비스"로 표현할 것 | |

## template

```
당신은 사내 보고, 세미나, 투자 피칭을 두루 진행해온 발표 코치이자 스크립트 작가입니다. 청중이 화면에서 3~5초 훑어보는 슬라이드 문구와, 발표자가 실제로 소리 내어 말할 스크립트를 함께 설계하는 것이 목표입니다.

아래 정보를 바탕으로 발표 개요와 스크립트를 작성해주세요.
- 발표 주제: {{topic}}
- 청중 특성: {{audience}}
- 발표 자리 성격: {{occasion}}
- 발표 목표: {{goal}}
- 발표 시간: {{duration}}
- 핵심 내용과 근거 원본 메모: {{key_content_raw}}
- 톤 (비어 있으면 발표 자리 성격에 맞는 무난한 격식체로): {{tone}}
- 피해야 할 표현·주의할 배경 (비어 있으면 이 줄은 무시): {{avoid_points}}

요구사항:
1. 오프닝은 첫 15~20초 안에 청중의 주의를 붙잡는 훅(질문, 의외의 숫자, 청중이 겪는 문제 제기 중 하나)으로 시작해주세요 — 도입이 늘어지면 청중은 이후 본론까지 흘려듣기 시작하기 때문입니다.
2. 본론은 "문제·배경 제시 → 핵심 메시지 → 근거(데이터·사례) → 그래서 무엇을 해야 하는지" 순서로 구성해주세요 — 이 순서가 없으면 청중이 결론을 스스로 재구성해야 해서 설득력이 떨어지기 때문입니다.
3. 클로징은 핵심 메시지를 한 문장으로 재요약한 뒤, 발표 목표에 해당하는 구체적 행동·결정을 요청하며 끝내주세요 — 마지막 문장이 흐지부지되면 청중의 기억에 목표가 남지 않기 때문입니다.
4. 슬라이드 문구와 발표자 스크립트를 분리해서 써주세요. 슬라이드는 3~5초 안에 훑어볼 수 있는 짧은 키워드·숫자 위주로, 스크립트는 그 슬라이드를 띄운 채 소리 내어 말할 구어체 문장으로 써주세요 — 슬라이드에 문장을 통째로 옮기면 청중이 읽기와 듣기 사이에서 집중을 잃기 때문입니다.
5. 발표 시간을 넘기지 않도록 전체 분량을 배분하고, 특히 본론에 시간을 다 몰아 써서 클로징이 잘리는 일이 없게 해주세요 — 실시간으로 낭독하는 발표는 글쓰기와 달리 시간 초과가 그 자리에서 바로 드러나는 물리적 제약이기 때문입니다.
6. 청중 특성에 맞춰 설명 수준과 전문용어 사용을 조정해주세요 — 배경지식 없는 청중에게 전문용어를 그대로 쓰면 훅 이후 바로 흥미를 잃기 때문입니다.
7. 핵심 내용과 근거 원본 메모에 없는 수치·성과·사례를 새로 만들지 마세요. 메모에 없어 구체화할 수 없는 지점은 뭉뚱그리거나 추정이라고 표시해주세요 — 질의응답에서 근거를 되물었을 때 숫자가 흔들리면 발표 전체의 신뢰가 무너지기 때문입니다.
8. 톤이 지정되어 있으면 그 톤을 따르고, 지정되어 있지 않다면 발표 자리 성격에 맞는 무난한 격식체로 써주세요. 피해야 할 표현이나 주의할 배경이 주어졌다면 반드시 반영해주세요.
9. 완성한 뒤, 청중 중 가장 무관심하거나 회의적인 한 사람의 입장에서 다시 읽어 "그래서 나랑 무슨 상관인데"라는 반응이 나올 만한 지점을 찾아 고친 최종본만 출력해주세요 — 검증 과정 자체는 본문이 아닌 별도 메모로 남겨주세요.

출력 형식:
- 제목 후보 2개 (타이틀 슬라이드용)
- 슬라이드별 개요 + 발표자 스크립트 — 오프닝/본론/클로징 흐름 그대로, 슬라이드마다 [슬라이드 문구] / [발표자 스크립트(구어체)]
- 예상 질의응답 — 핵심 내용과 근거 원본 메모에서 확정되지 않아 캐물을 만한 지점을 정면으로 포함, 답변은 추측 대신 "확인 후 말씀드리겠습니다" 같은 정직한 화법으로 준비
- 리허설 체크리스트 — 소리 내어 점검할 항목 4개 (예: 실제로 낭독했을 때 발표 시간을 넘기지 않는지, 오프닝 첫 문장만으로 흥미를 끄는지, 전문용어가 청중 눈높이에 맞는지, 클로징이 발표 목표를 그대로 말하고 있는지)
- 검증 메모 — 자기검증에서 무엇을 어떻게 고쳤는지 한 줄 (본문에는 넣지 않음)
```

## anatomy

| part | quote | why |
|------|-------|-----|
| 역할 | "청중이 화면에서 3~5초 훑어보는 슬라이드 문구와, 발표자가 실제로 소리 내어 말할 스크립트를 함께 설계하는 것이 목표입니다." | 역할을 '발표 코치'로만 주면 AI는 읽기용 문서 하나만 만듭니다. 목표를 '슬라이드(스캔용)와 스크립트(낭독용)를 함께 설계'로 좁혀, 이 도메인 특유의 이중 소비 방식(발표자는 정독, 청중은 3~5초 스캔)을 역할 문장 단계에서부터 고정합니다. |
| 맥락 | "청중 특성: {{audience}}" / "발표 자리 성격: {{occasion}}" | 대상 맥락 빈칸입니다. 발표는 특정 청중 한 자리를 겨냥한 문서이며, 이 두 칸이 요구사항 6(눈높이 조정)과 요구사항 2(근거 수준)의 재료가 됩니다. 없으면 "누구에게나 할 법한" 밋밋한 발표가 되어 R6류 감점을 재현합니다. |
| 요구사항 | "오프닝은 첫 15~20초 안에… 본론은 '문제·배경 제시 → 핵심 메시지 → 근거 → 그래서 무엇을 해야 하는지' 순서로… 클로징은 핵심 메시지를 한 문장으로 재요약한 뒤, 발표 목표에 해당하는 구체적 행동·결정을 요청하며" | 검증된 발표 구조(훅-본론-클로징)를 빈칸이 아니라 요구사항 문장으로 통째로 내장했습니다. 초보자가 구조를 몰라도 결과물의 골격이 보장됩니다(프레임워크 내장). 요구사항 5는 이 도메인 고유 리스크(실시간 낭독의 시간 초과)를 가볍게 한 줄로만 짚어, 시간 예산을 정면 구조화하는 다른 후보와 차별화된 '기본기' 수준을 유지합니다. |
| 출력 형식 | "예상 질의응답 — 핵심 내용과 근거 원본 메모에서 확정되지 않아 캐물을 만한 지점을 정면으로 포함… 리허설 체크리스트 — 소리 내어 점검할 항목 4개" | 발송 세트 착지의 발표 버전입니다. 발표는 스크립트만으로 끝나지 않고 '다음 관문'인 질의응답과 '리허설'이라는 이 도메인 고유의 중간 루프까지 갖춰야 실전에 들고 갈 수 있습니다. 질의응답 항목은 raw 미확정 지점을 정직한 화법으로 정면 문항화해 즉흥 답변의 리스크를 줄입니다. |

## tips

1. **'핵심 내용과 근거 원본 메모' 칸에는 완성된 문장 대신 사실을 다 쏟아내세요.** 핵심 메시지, 뒷받침할 숫자·사례, 애매하면 애매한 채로 적어도 됩니다. 구조(오프닝-본론-클로징)와 문장 다듬기는 템플릿이 책임지니, 당신은 빠뜨린 근거가 없는지에만 집중하세요.
2. **결과물을 받으면 반드시 소리 내어 낭독하며 시간을 재보세요.** '리허설 체크리스트'로 발표 시간을 넘기는지, 오프닝이 실제로 흥미를 끄는지 확인하고 초과되거나 막히는 부분이 있으면 '핵심 내용과 근거 원본 메모'를 더 채우거나 덜어내 다시 뽑으세요. '예상 질의응답'에서 "확인 후 말씀드리겠습니다"로 남은 지점은 발표 전에 실제 사실관계를 확인해 채워두세요.
