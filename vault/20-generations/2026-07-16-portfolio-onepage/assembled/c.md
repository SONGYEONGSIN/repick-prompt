요구사항:
1. 페이지에 실리는 모든 문장과 숫자는 위 프로젝트 메모에 적힌 사실 안에서만 쓰세요. 메모에 없는 수치·기간·수상·고객 반응을 지어내지 마세요 — 포트폴리오의 문구 하나하나는 면접과 미팅에서 질문 대상이 되고, 주인이 근거를 대지 못하는 문장 하나가 페이지 전체의 신뢰를 무너뜨리기 때문입니다.
2. 메모가 뭉뚱그린 부분(정확한 수치·시점·역할 범위)은 그럴듯하게 특정하지 말고, 뭉뚱그린 그대로 쓰거나 그 자리에 [확인 필요]라고 표시하세요 — "약 40%"를 "42.3%"로 만드는 순간 확인 질문에 무너지는 약점이 되지만, [확인 필요]는 게시 전에 주인이 채우면 그만이기 때문입니다.
3. 각 프로젝트는 결과물 나열이 아니라 "어떤 문제였나 → 나는 어떻게 접근했나 → 결과는 무엇으로 확인됐나"의 3단 케이스로 서술하세요 — 결과만 보여주면 '무엇을 했는지'는 알아도 '어떻게 생각하는 사람인지'는 알 수 없고, 보는 사람이 정말 판단하려는 것은 후자이기 때문입니다.
4. 팀으로 한 프로젝트는 내가 맡은 부분과 팀이 함께 한 부분을 문장에서 구분하고, 팀 성과를 "내가 해냈다"로 쓰지 마세요 — 역할을 뭉뚱그린 '우리'는 전체를 내 것처럼 보이게 하는 과장이라, 같이 일한 사람 한 명의 증언만으로도 뒤집히기 때문입니다.
5. 인터랙션은 세 가지만 넣으세요: 프로젝트 카드를 누르면 케이스 전문이 펼쳐지는 동작, 상단 메뉴에서 각 섹션으로 이동하는 앵커, 펼침과 이동 시의 부드러운 전환. 자동 재생 애니메이션·파티클·마우스를 따라다니는 효과는 넣지 마세요 — 인터랙션의 역할은 증거를 읽기 좋게 돕는 것이고, 화려한 효과는 내용의 빈약함을 가리려는 신호로 먼저 읽히기 때문입니다.
6. 눌리는 모든 요소는 실제로 반응하게 만드세요. 위 '작업물 링크'에 적힌 링크만 실제 주소로 연결된 버튼으로 만들고, 링크가 없는 프로젝트에는 '보러 가기' 버튼 자체를 만들지 마세요 — 눌렀는데 아무 데도 가지 않는 버튼은 링크가 없는 것보다 나쁜, 준비 안 된 인상을 남기기 때문입니다.
7. 이미지 없이 타이포그래피·여백·2~3가지 색만으로 완성되는 페이지로 만들고, 모든 코드(HTML·CSS·JavaScript)를 하나의 .html 파일에 담아 인터넷 연결 없이 더블클릭만으로 열리게 하세요 — 코드를 모르는 사람은 이미지 경로나 외부 파일이 하나만 어긋나도 스스로 고칠 수 없기 때문입니다.
8. 휴대폰 화면에서 먼저 잘 읽히게 만드세요. 글자는 충분히 크게, 카드는 한 손 엄지로 펼치기 쉽게요 — 포트폴리오 링크는 대부분 메신저나 메일을 통해 폰에서 처음 열리기 때문입니다.
9. 페이지 완성 후 출력 전에, 위 '볼 사람'이 되어 페이지를 읽으며 "이거 근거 있어요?"라고 짚을 만한 문구 3개를 찾으세요. 각 문구를 메모 원문과 대조해 근거 문장이 있으면 그대로 두고, 없으면 지우거나 [확인 필요]로 바꾼 최종본만 출력하세요 — 보는 사람의 첫 검증 질문을 게시 전에 미리 맞아보는 것이 실제 미팅에서 무너지는 것보다 훨씬 싸기 때문입니다. 이 점검 내용은 페이지 본문에 넣지 말고 아래 '사실 대조표'로만 분리하고, 항목마다 근거가 된 메모 원문을 짧게 인용하세요 — 인용할 원문이 없는 항목은 그 자체가 새로 만들어낸 주장이라는 신호이기 때문입니다.

출력 형식:
- 완성된 단일 HTML 파일의 전체 코드 (생략이나 "…이하 동일" 없이, 복사해서 붙여넣기만 하면 되는 완전한 코드)
- 파일 여는 법 3단계: 메모장(텍스트 편집기)에 코드 붙여넣기 → "포트폴리오.html" 이름으로 저장 → 저장한 파일 더블클릭
- 사실 대조표: 페이지에 실린 성과·수치 문구 각각에 대해, 근거가 된 메모 원문을 짧게 인용해 나란히 붙인 표
- [확인 필요] 목록: 게시 전에 주인이 채우거나 지워야 할 자리와, 각각을 확인하는 방법 한 줄
- 예상 검증 질문 3개: 볼 사람이 던질 법한 사실 확인 질문과, 메모에 근거해 답할 수 있는 답변 포인트 한 줄씩
