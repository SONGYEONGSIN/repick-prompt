## 소거 카드

### 후보 1: DB 인스턴스 타입 변경 작업

- **후보 사건 (raw 인용):** "14:15 - 인프라팀(박도현) 슬랙: 'DB 인스턴스 타입 변경(db.r6g.xlarge → db.r6g.2xlarge) 작업 시작합니다, 무중단 전환 예정'"
- **지지 근거 (원문 인용):** 작업 시작 시각(14:15)이 5xx 에러율 상승 시작(14:20)보다 앞서고, "저희 쪽 작업은 14:15~14:50 사이 진행됐고" (박도현, 14:52)라는 진술상 작업 구간이 증상 구간(14:20~14:45) 전체를 포괄함 — 시간적 중첩만 확인됨.
- **반박 근거 (원문 인용):** "전환 자체는 무중단으로 설계된 절차라 커넥션 끊김은 없었어야 합니다. 확인 필요하시면 인스턴스 전환 로그 공유드릴게요" (박도현, 14:52) — 다만 이는 "무중단으로 설계됐다"는 절차상 의도에 대한 진술이며, 발화자 스스로 "확인 필요하시면 로그 공유드릴게요"라고 덧붙여 로그를 통한 실제 검증은 아직 이루어지지 않았음을 명시하고 있음.
- **경로가 raw에 있는지:** 없음. raw 어디에도 DB 인스턴스 전환이 결제 API의 DB 커넥션 풀 고갈이나 응답 지연을 구체적으로 어떻게 유발했는지 설명하는 진술이 없음. 반면 아래 후보 2에서는 캐시 미스 → 동기 호출 → 커넥션 점유 → 풀 고갈이라는 구체적 경로가 APM 트레이스로 제시됨.
- **판정:** **보류** — 경로를 제시하는 raw 진술이 없고(요구사항 3), 유일한 반박 진술도 발화자 본인이 로그 기반 확정 검증이 아직 안 됐다고 밝힌 설계 의도 수준의 진술이므로 확정 소거 근거로 보기 부족함. 채택할 경로 근거도 없으므로 채택 불가.

- **반박 근거 (원문 인용):** "결제 서비스 재시작 실행 (에러율 6.1%→1.8%로 일시 완화)" — 재시작 직후 에러율이 오히려 낮아졌다는 raw 진술 자체가, 재시작을 증상의 '원인'으로 보는 것과 정면으로 배치됨(원인이라면 재시작 후 악화되어야 하나 raw는 개선을 기록). 또한 재상승 시점(14:36)에도 v2.14.0은 아직 롤백 전(롤백은 "14:40 - 한지훈: v2.14.0 롤백 실행")이므로, raw상 재상승은 후보 2(v2.14.0)의 근본 결함이 재시작 이후에도 지속된 결과로 이미 설명됨.

- **판정:** **소거** — 재시작이 증상을 완화시켰다는 raw의 직접 진술이 존재하여, 재시작을 원인으로 보는 것을 명시적으로 반박함.

## 감별 결론

**최종 채택된 원인: 결제 서비스 v2.14.0 배포(Redis 캐싱 로직 추가, PR #1842)의 캐시 키 설계 결함.** 사용자별 재고 조회 파라미터가 캐시 키에 섞여 들어가 캐시 히트가 거의 발생하지 않았고(미스율 평균 87%), 미스마다 재고 확인 API를 동기 호출해 DB 커넥션을 정상 대비 약 8배(3.2초 대 0.4초) 오래 점유하면서 커넥션 풀(사이즈 50)이 고갈되어 신규 결제 요청의 응답 지연과 5xx 급증으로 이어졌다.

- **DB 인스턴스 타입 변경 작업이 아닌 이유(보류):** raw에 이 작업이 결제 API 지연을 유발한 구체적 경로가 없고, 박도현의 "무중단 설계이므로 문제 없었어야 한다"는 진술도 본인이 로그 기반 재확인이 필요하다고 명시해 확정 반박으로 보기 부족하므로, 채택도 소거도 아직 불가.
- **결제 서비스 재시작이 아닌 이유(소거):** 재시작 직후 에러율이 6.1%→1.8%로 낮아졌다는 raw 기록이, 재시작을 증상의 원인으로 보는 것과 직접 모순되며, 이후 재상승은 아직 롤백되지 않은 v2.14.0의 결함이 지속된 결과로 raw 타임라인상 이미 설명됨.

## 재발방지 조치 후보와 결정 요청

raw에서 논의 중인 재발방지 조치는 다음 두 가지이며, 어느 쪽이 근본 해결책인지는 이 보고서가 임의로 결론 내리지 않는다.

1. **결제 서비스 DB 커넥션 풀 사이즈(현재 50) 확대** — [추가 사실]에서 재발방지 조치로 논의 중이라고 명시됨.
2. **캐시 키 설계 재검토** (사용자별 파라미터를 캐시 키에서 배제 등) — [추가 사실]에서 "캐시 키 설계를 고치는 것이 근본 해결책인지"가 이 문서가 답해야 할 질문 중 하나로 명시됨. 다만 "캐시 키 설계 시 사용자별 파라미터를 배제해야 한다는 별도 내부 가이드라인이 있었는지는 이번 조사 범위에서 확인되지 않음(raw에 언급 없음)".

**결정 요청:** 두 조치 중 최종 선택은 승인권자인 **윤서준(CTO)**에게 넘긴다. 승인 판단에 앞서 **김서아(결제팀 테크리드)**의 PR #1842 캐시 키 설계 결정 배경 확인이 선행되어야 한다.
