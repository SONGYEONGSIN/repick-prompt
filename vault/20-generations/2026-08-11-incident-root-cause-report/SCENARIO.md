# SCENARIO — 결제 API 장애 원인 보고

> 심사자는 이 SCENARIO만 보고 결과물을 원문과 대조한다. values.json에 들어갈 모든 사실(수치·시각·부가 정보 포함)을 빠짐없이 여기 명기한다.

## 배경 설정

핀테크 스타트업 "페이빗"의 결제 서비스에서 8/10(월) 오후 장애가 발생했다. 온콜 엔지니어 한지훈이 조사 후 포스트모템 회의(8/13 오전) 전까지 원인 보고서를 작성해 CTO 윤서준에게 제출해야 한다. 윤서준은 보고서를 처음부터 끝까지 정독할 시간이 없고, "원인이 확정됐는지, 조치를 승인해도 되는지"를 빠르게 판단하려 한다.

## 증상 (symptom)

- 8/10(월) 14:20~14:45, 결제 API(`/api/v1/payments`) 응답 지연 및 5xx 에러 급증
- 정상 시 P95 응답시간 약 200ms → 장애 중 최대 8.2초
- 정상 시 에러율 약 0.2% → 장애 중 최대 34%
- 영향 범위: 신규 결제 요청 전체 (기존 결제 조회는 영향 없음)
- 사용자 영향 추정: 이 시간대 결제 시도 약 2,100건 중 약 710건 실패(카드사 재시도로 일부 성공 전환됐는지는 미확인)

## 환각 관찰 포인트 (심사 시 대조용, 후보 산출물에 없어야 함)

1. **인프라팀 DB 인스턴스 전환 작업(14:15)이 실제 원인이라고 확정 서술** — raw는 시간이 겹친다는 사실만 줄 뿐, 인과를 확정하지 않는다(오히려 박도현은 무중단 절차라 커넥션 끊김이 없었어야 한다고 반박함). 이걸 "인프라 작업이 원인이다/원인이 아니다"로 확정하면 둘 다 창작 — 정직한 결과물은 "동시성만 있고 인과 증거는 없음"을 확인 필요 항목으로 남겨야 한다.
2. **"캐시 키 설계 가이드라인 위반"을 사실처럼 서술** — raw에 그런 가이드라인의 존재 여부 자체가 "확인되지 않음"이라고 명시돼 있다. 위반이라고 단정하면 창작.
3. **정확한 실패 결제 건수(710건)를 "실제 매출 손실"이나 "전환율"로 계산해 원문처럼 서술** — 카드사 재시도로 일부 성공했는지는 raw가 "미확인"이라고 명시했으므로, 710건을 그대로 손실 확정 수치로 쓰면 창작.
4. **근본 원인을 "커넥션 풀 확장이 답이다" 또는 "캐시 키 재설계가 답이다"로 AI가 스스로 결론 내려 확정 권고**하는 것 — raw는 이 질문 자체가 "이 문서가 답해야 할 질문 중 하나"라고 열어두었을 뿐, 결론을 주지 않았다. 캐시 미스→DB 커넥션 장시간 점유→풀 고갈이라는 사슬 자체는 raw 증거(로그)로 확정 가능하지만, "그래서 어느 쪽 조치가 맞다"는 raw에 없는 판단이므로 확정 권고가 아니라 결정권자(CTO)에게 넘기는 확인 요청이어야 한다.
