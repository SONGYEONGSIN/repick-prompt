# DOMAIN — 채용 공고 작성 (R24)

> named query 실행. 근거: DNA v1.21, ledger 최근 5개(R19~R23), MEMORY.md.

## 1. 본질 리스크

채용 공고가 실패하는 1순위 원인은 두 갈래다. 첫째는 **형용사만 있는 자격요건**("책임감 있는", "열정적인 인재") — anti-slop 금지 규칙이 이미 봉쇄해온 패턴이지만, 채용 공고는 이 실패가 가장 노골적으로 반복되는 장르다. 검증 불가능한 인성 형용사는 지원자 자기선별을 못 시켜 부적합 지원자만 늘린다. 둘째, 더 치명적인 리스크는 **위법·차별적 조건의 노출**이다 — 채용절차법·남녀고용평등법은 채용 공고에 성별·연령·혼인여부·가족상황·용모 등을 조건으로 명시하거나 이를 이유로 불리하게 다루는 것을 금지한다. 소규모 팀의 대표가 "오래 다닐 사람이면 좋겠다"는 정당한 니즈를 "20대 여성이면 좋겠다"는 위법한 표현으로 raw 메모에 섞어 넣는 경우가 실무에서 흔하다 — product-detail-page(R8)가 봉쇄한 "위법 효능 요구가 raw에 섞여도 필터링되는가"와 같은 구조의 함정이 채용 도메인에서 재현된다.

## 2. 본질 루프

"만들면 끝"에 가깝다 — press-release(R23)처럼 게시 시점에 완성되는 문서로, 채용이 마감되면 공고 자체의 생명주기가 끝난다. 다만 지원자가 적으면 공고를 수정해 재게시하는 경우가 있으나, 이는 광고(R20)의 예산 소진형 반복 측정 루프와는 다르다 — 성과 판정 카드가 본질은 아니다.

## 3. 결과물의 소비 방식

지원자는 원티드·잡코리아 같은 채용 플랫폼에서 하루 수십 개 공고를 훑으며 **제목과 자격요건 목록만 보고 지원 여부를 즉시 판단**한다 — press-release(R23)의 "기자의 3초 스캔"과 구조가 같다. 다만 기자는 "기사화할 가치"를 판단하지만 지원자는 "내가 이 조건에 맞는가/맞고 싶은가"를 자기선별한다는 점이 다르다. 자격요건이 모호하면 부적합자만 지원하고 적합자는 이탈한다.

## 4. 유사 라운드 전례

- press-release (R23) — raw 범위 밖 창작 금지 + 근거 없는 형용사(자화자찬) 금지. 채용 공고는 "자화자찬형 수식어"가 "인성 형용사"로 형태만 바뀐 동일 리스크.
- cs-reply (R7) — 불가능한 요구는 얼버무리지 말고 명시 봉쇄 + 대안. 채용 공고의 위법 조건 리스크는 이 원칙의 변형("지킬 수 없는 약속"이 아니라 "써서는 안 되는 조건")이다.
- product-detail-page (R8) — 판매자가 위법 효능 요구를 raw에 섞어도 필터링되는지 검증한 함정. 채용 도메인 재현 대상.
- resume (R9) / cover-letter (R6) — 커리어 카테고리의 기존 3종은 전부 구직자 관점. 채용 공고는 고용주 관점의 거울상 문서로, "대상 맥락 빈칸"(R6·R7) 원칙이 여기선 "채용 담당자가 원하는 인재상"이 아니라 **"이 조건을 보고 지원할 후보자가 실제로 궁금해할 것"** 쪽으로 뒤집힐 가능성이 있다.

## 5. 방향 풀 추천

- **a = 결합형 표준** — 채용 공고 표준 구조(회사 소개 → 포지션 소개 → 주요 업무 → 자격요건 → 우대사항 → 근무조건 → 전형절차 → 지원 방법) 프레임워크 내장 + 코치형 help + raw 범위 빈칸. 기본 포함.
- **b = 위법·차별 표현 봉쇄형 (도메인 본질 겨냥)** — 성별·연령·혼인여부·가족상황·용모 등 채용절차법·남녀고용평등법이 금지하는 조건을 요구사항 문장에서 정면으로 배제하도록 명시하고, raw 메모에 그런 조건이 섞여 있으면 그 밑에 깔린 정당한 니즈(예: 장기 근속 의향)로 치환해서만 반영하라는 자기검증을 내장한다. 형용사만 있는 자격요건 대신 "검증 가능한 최소 기준 + 우대사항" 분리도 요구사항에 못박는다.
- **c = XML 구조 태그 (방향 가설 대기열 소비)** — **a와 완전히 동일한 필드·요구사항 내용**을 유지하되, 본문 템플릿에서 4요소(역할·맥락·요구사항·출력형식) 경계를 현재 관행(역할은 무라벨 산문, 맥락은 "아래 정보를 바탕으로" 불릿, 요구사항/출력형식은 콜론 라벨)이 아니라 XML 태그(`<역할>`·`<맥락>`·`<요구사항>`·`<출력형식>`)로 명시적으로 감싼다. R22→R23이 확립한 "통제쌍" 방법론을 그대로 적용해, a와 c의 유일한 차이를 구조 표기 방식 하나로 고정함으로써 XML 태그 자체의 순효과를 격리한다.

**예측**: b(위법·차별 표현 봉쇄형, 도메인 본질 겨냥)가 우세할 것으로 예상 — R7·R8·R23이 보여준 "raw에 섞인 위법·불가능 요구를 정면 봉쇄하는 방향"이 이 도메인의 본질 리스크(법적 문제)와 직접 맞닿아 있다. 다만 a/c 통제쌍에서 c가 이긴다면 XML 구조 태그의 순효과가 처음으로 분리 확인된다. (domain-fit 예측 누적 4승 6패, 이번이 7차 검증)
