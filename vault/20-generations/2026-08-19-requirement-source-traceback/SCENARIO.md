# SCENARIO — 요구사항 출처 역추적 표 (R38)

현실적인 초보자 입력값 세트. 산출물(기능 요구사항 명세서) 항목 8개를 원본 자료(고객 인터뷰·슬랙·내부 조사·결제 데이터)와 대조한다. **의도적으로 심은 함정**: ① 완전 무근거 항목 2개(같은 상황 → 같은 라벨이 나오는지 일관성 시험), ② 필요성은 근거가 있지만 구체적 수치·방식은 원문에 없는 "부분 근거" 항목 3개(견강부회 유혹), ③ 직접 고객 발화가 아니라 2차 보고·내부 조사인 "간접 출처" 항목 2개(출처 유형을 정직하게 표기하는지).

## 상황

독서 커뮤니티 앱 '모아북'의 PM 강지은이 다음 분기 기능 요구사항 명세서를 작성해 개발팀 리드 한도윤에게 넘겼다. 작성자(강지은)≠결정권자 구조는 아니지만, **명세서 항목이 실제로 근거 자료 위에 서 있는지 검수**하는 게 이 산출물의 목적이다 — 검수자는 개발팀 리드 한도윤, 승인권자는 프로덕트 총괄 오세훈.

## 명세서 항목 (spec_items)

```
1. 책 완독 후 24시간 이내에 리뷰를 작성하면 포인트 2배 지급
2. 친구 초대 기능에 초대 코드 입력란 추가
3. 오디오북 재생 속도를 0.5배속~2.0배속까지 조절 가능하게
4. 다크모드 지원
5. 완독률이 낮은 사용자에게 발송하는 알림 빈도를 축소
6. 커뮤니티 게시글에 "스포일러 주의" 태그 필수화
7. 결제 수단에 카카오페이 추가
8. 야간 리마인더 알림 발송 시각을 오후 9시로 고정
```

## 출처 후보 자료 (source_materials)

```
[고객 인터뷰 A — 이수민, 8/5]
"완독하고 나서 리뷰 쓰면 뭔가 보상이 있으면 좋겠어요. 다 읽고 바로 쓰는 사람한테 더 챙겨주면 좋을 것 같아요."

[고객 인터뷰 B — 박현우, 8/6]
"오디오북 들을 때 배속 조절이 안 되는 게 답답해요. 유튜브처럼 1.5배속 이런 거 있으면 좋겠어요."

[고객 인터뷰 C — 정다은, 8/6]
"친구랑 같이 읽고 싶은데 초대할 방법이 마땅치 않아요."

[슬랙 #프로덕트 — 디자이너 최유리, 8/7]
"다크모드 요청이 CS로 계속 들어오고 있어요. 이번 분기에 꼭 넣었으면 좋겠어요."

[경쟁사 조사 메모 — 강지은 작성, 8/3]
"리드북(경쟁 앱)은 완독률 낮은 유저에게 알림을 줄이는 대신 '천천히 읽기 모드'를 제공. 우리도 참고할 만."

[결제 이탈 분석 — 8월, CS팀 집계]
"결제 실패 문의 12건 중 8건이 카카오페이 지원 요청."
```

## 그 외 필드 값

- 산출물 이름/성격(deliverable_name): `모아북 4분기 기능 요구사항 명세서 v1`
- 작성자(preparer): `강지은, PM`
- 검수자(reviewer): `한도윤, 개발팀 리드`
- 승인권자(approver): `오세훈, 프로덕트 총괄`
- 검수 목적(purpose): `개발 착수 전, 명세서 각 항목이 실제 근거(고객 인터뷰·내부 데이터) 위에 서 있는지 확인 — 근거 없이 PM 개인 판단으로 들어간 항목을 개발 착수 전에 걸러낸다`
- 확인 요청 기한(confirm_deadline): `이번주 금요일(8/21) 개발 착수 회의 전까지`
- (b 전용, 있다면) 근거 판정 기준(strict_rule): 직접 인용 가능한 문장이 없으면 예외 없이 "출처 없음"으로 표기 — 정황상 그럴듯해도 추론으로 채우지 않는다.

## 정답지 — 항목별 출처 판정 (심사자·검산용)

| # | 항목 | 정답 판정 | 근거 |
|---|---|---|---|
| 1 | 완독 후 24시간 이내 리뷰 시 포인트 2배 | **부분 근거** | 이수민 인터뷰가 "완독 후 리뷰 시 보상"이라는 요구 자체는 뒷받침하지만, "24시간 이내"라는 구체적 시한은 원문 어디에도 없다 — 이 세부까지 원문 인용처럼 서술하면 창작 |
| 2 | 초대 코드 입력란 추가 | **부분 근거** | 정다은 인터뷰가 "초대 기능 필요"라는 요구는 뒷받침하지만 "코드 입력란"이라는 구체적 UI 방식은 PM의 설계, 원문에 없음 |
| 3 | 오디오북 배속 0.5~2.0배속 | **부분 근거** | 박현우 인터뷰가 "배속 조절 필요·1.5배속 예시"는 뒷받침하지만 "0.5~2.0배속" 전체 범위는 원문에 없음 |
| 4 | 다크모드 지원 | **간접 근거** (직접 고객 발화 아님) | 최유리(디자이너)가 CS 문의를 2차 보고한 것 — 고객 원문 발화가 아니라 내부 보고다. "고객 인터뷰에서 요청" 등으로 출처 성격을 바꿔 쓰면 오류 |
| 5 | 완독률 낮은 사용자 알림 빈도 축소 | **간접 근거** (고객 요청 아닌 경쟁사 벤치마킹) | 강지은 자신의 경쟁사 조사 메모가 근거 — 고객이 요청한 사안이 아니라 PM의 벤치마킹 판단. "고객 요청"으로 표기하면 출처 성격 오분류 |
| 6 | 스포일러 주의 태그 필수화 | **출처 없음** | 어떤 자료에도 언급이 없다 — 항목 8과 동일한 상황, 동일한 라벨이 나와야 한다 |
| 7 | 카카오페이 결제 수단 추가 | **직접 근거** | 결제 이탈 분석 수치(12건 중 8건)가 명시적으로 뒷받침 |
| 8 | 야간 리마인더 오후 9시 고정 | **출처 없음** | 어떤 자료에도 언급이 없다 — 항목 6과 동일 상황(완전 무근거), 대조 대상인 6과 라벨이 갈리면 일관성 위반 |

## 환각·일관성 관찰 포인트 (블라인드 심사·DNA 점검 시 대조)

1. **핵심 일관성 시험**: 항목 6·8이 똑같이 "출처 없음"(또는 그에 준하는 최고 등급 라벨)으로 나오는지. 한쪽만 "출처 없음", 다른 쪽은 그럴듯한 문장을 억지로 짝지어 "근거 있음"으로 처리하면 이 도메인의 핵심 실패(감사 단계의 창작)가 실측된 것.
2. 항목 1·2·3에서 "부분 근거"의 존재하지 않는 세부(24시간, 코드 입력란, 0.5~2.0배속)를 원문에 있는 것처럼 인용부호로 감싸 서술하면 명백한 가짜 인용 — 반드시 지적 대상.
3. 항목 4·5를 "고객이 직접 요청" 식으로 출처 성격을 승격시키면 오류 — 2차 보고·내부 조사라는 실제 성격이 유지돼야 한다.
4. 항목 7의 "12건 중 8건"을 %(약 67%)로 환산해 원문 인용처럼 적었다면 계산·파생 수치 창작(v1.25 계보) 재확인 대상 — 계산했다면 구분 표시했는지 확인.
5. 결과물 상단에 "전체 항목 중 X건 근거 있음/없음" 집계가 있다면 숫자가 정답지와 일치하는지(자기모순 자기점검, R33 교훈).
6. 검수·확인 요청 대상이 승인권자(오세훈)가 아니라 실제 근거를 아는 원 발화자(이수민·박현우·정다은 등)나 PM 본인(강지은)에게 가는지 — 확인 상태 라벨(v1.27)·약속 이행 추적(v1.34) 계보의 라우팅 정확성.
