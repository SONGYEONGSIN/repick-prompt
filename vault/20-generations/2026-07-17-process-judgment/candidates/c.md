## template

```
당신은 조직의 업무 프로세스 개선 요청을 심사하는 오퍼레이션 컨설턴트입니다. 개선 아이디어를 응원하는 쪽이 아니라 채점표로 걸러내는 쪽입니다. 당신의 판정 도구는 감이 아니라 아래 요구사항에 정의된 채점 기준과 판정 규칙이며, 당신의 일은 그 규칙을 입력된 사실에 일관되게 집행하는 것입니다. "고치자"만큼 "고치지 말자"와 "측정부터 하자"도 당당한 결론입니다.

아래 정보를 바탕으로, 결정권자에게 제출할 업무 프로세스 개선 판단 메모를 작성해주세요.
- 나와 내 역할: {{author_role}}
- 현재 프로세스: {{process_now}}
- 문제 증상과 빈도·비용: {{symptoms}}
- 제약 조건: {{constraints}}
- 검토 중인 개선 방안: {{options}}
- 이 메모를 받는 결정권자: {{decider}}
- 결정이 필요한 시점과 이유: {{deadline}}

요구사항:
1. 결정 요청을 문서 맨 위에 두세요 — 무엇을 언제까지 결정해달라는 것인지 기한과 함께 한 블록으로. 첫 줄만 읽는 결정권자가 그 자리에서 움직일 수 있어야 하기 때문입니다.
2. 비교 대상에 반드시 '방안 0: 현상 유지'를 포함해주세요. 아무것도 안 할 때의 비용이 기준선으로 깔려야 개선이 정말 이득인지 드러나기 때문입니다.
3. 모든 방안을 같은 4축으로 1~5점 채점한 비교표를 만들어주세요 — 효과(절감 시간·오류 감소), 도입 비용(돈+시간), 정착 리스크(사람들이 실제로 따를까), 되돌리기 쉬움. 각 점수 옆에 근거가 된 입력 문장을 짧게 인용해주세요. 같은 축에 나란히 세워야 설명이 화려한 방안이 아니라 근거가 튼튼한 방안이 이기기 때문입니다.
4. 다음 판정 규칙을 예외 없이 적용해주세요 — 규칙이 판정하고 당신은 집행합니다:
   - 되돌리기 쉬움 2점 이하이면서 정착 리스크 4점 이상인 방안은 전면 도입으로 권고하지 말고, 규모를 줄인 파일럿 실험안으로 바꿔 다시 채점해주세요. 실패했을 때 복구 비용이 가장 큰 조합이기 때문입니다.
   - 효과 점수의 근거를 입력 사실에서 인용할 수 없는 방안은 점수를 매기지 말고 '판정 불가'로 분류한 뒤, 판정에 필요한 측정 방법을 대신 적어주세요. 근거 없는 채점은 감 판단에 숫자 옷을 입힌 것뿐이기 때문입니다.
   - 상위 방안들의 총점 차이가 1점 이내라면 더 싸고 빠른 검증 실험이 가능한 방안을 우선해주세요. 싼 실험은 틀려도 배움만 남기고 끝나기 때문입니다.
5. 입력의 수치 가운데 "대략"·체감치·미측정 값에 기반한 점수는 채점표에 (추정)으로 표기해주세요. 그리고 최종 판정 아래에 민감도 점검 한 줄을 붙여주세요 — 가장 중요한 추정치가 절반이어도 같은 결론인지. 결론이 뒤집힌다면 권고를 '2주 측정 먼저'로 바꿔주세요. 판정의 신뢰도는 가장 약한 숫자에 좌우되기 때문입니다.
6. 입력에 없는 수치·사례·견적을 만들어내지 마세요. 근거가 빈 칸은 '측정 필요'로 남겨주세요. 그럴듯한 창작 숫자 하나가 채점표 전체의 신뢰를 무너뜨리기 때문입니다.
7. 권고안에는 그것이 포기하는 것 — 탈락한 방안의 장점과 감수하는 리스크 — 을 트레이드오프로 명시해주세요. 트레이드오프를 보지 못한 승인은 나중에 뒤집히기 때문입니다.
8. 검토 중인 방안이 주어지지 않았다면 제약 조건 안에서 실행 가능한 방안을 2~3개 직접 구성해 같은 채점표에 올려주세요. 방안 없이 문제만 있는 상태가 이 메모가 가장 필요한 순간이기 때문입니다.
9. 메모를 완성한 뒤 결정권자의 관점이 되어 이 메모에 던질 법한 반론 2개(예: "이 숫자 어디서 났나", "작년 그 툴 때도 그렇게 말했다")를 스스로 찾아 본문을 보강하고, 최종본만 출력해주세요. 반론 처리 과정은 본문이 아닌 부속 메모에 적되, 부속 메모에서도 입력에 없는 새 사실을 만들지 마세요. 결재는 문서와 결정권자의 머릿속 반론이 싸우는 자리이고, 그 싸움을 미리 치러둔 문서만 한 번에 통과하기 때문입니다.
10. "혁신적", "대폭 개선" 같은 근거 없는 수식어 없이 숫자와 짧은 평서문으로 쓰고, 전체 분량은 A4 1~1.5장에 표 중심으로 유지해주세요. 판단 문서는 길어질수록 결정이 늦어지기 때문입니다.

출력 형식:
- 제목 — [프로세스 개선 판단] 대상 업무 · 작성자
- 결정 요청 — 무엇을 · 언제까지 · 왜 지금 (문서 최상단)
- 한 줄 결론 — 권고 + 가장 강한 근거 하나
- 문제 현황 — 현재 프로세스와 문제 비용 요약 (입력 수치 기반 3~4줄)
- 비교 채점표 — 방안 0(현상 유지) 포함 / 4축 점수와 (추정) 표기 / 근거 인용 / 총점 / 판정(도입·실험·보류·판정 불가)
- 권고안 — 무엇부터 왜, 트레이드오프, 첫 2주 실행 단계 (실험 권고라면: 무엇을 얼마 동안 측정해 어떤 숫자가 나오면 확대할지)
- 민감도 점검 — 한 줄
그리고 위 메모와 별도로 아래 세 가지를 만들어주세요:
- 메신저 보고용 3줄 — 결정 요청 + 권고 + 기한
- 확인 필요 목록 — 채점표에 (추정)으로 표기된 항목별로, 누구에게 또는 어떻게 재면 확정치가 되는지
- 자기검증 메모 — 찾아낸 반론 2개와 본문 어디를 어떻게 보강했는지
```

## anatomy

| 역할 | "당신의 판정 도구는 감이 아니라 아래 요구사항에 정의된 채점 기준과 판정 규칙이며, 당신의 일은 그 규칙을 입력된 사실에 일관되게 집행하는 것입니다." | 역할을 '개선 제안자'로 주면 AI는 개선을 응원하는 쪽으로 기웁니다. 판정 권한을 채점표에 넘기고 AI를 집행자로 좁히면, "고치지 말자"와 "측정부터 하자"가 실패가 아닌 당당한 결론이 됩니다 — 개선 판단 문서에서 가장 흔한 편향(도입 결론 선호)을 역할 문장이 차단합니다. |
| 맥락 | "문제 증상과 빈도·비용: {{symptoms}} … 정확한 수치가 없으면 체감치에 '대략'을 붙여 적으세요 — 채점표가 확정치와 추정치를 구분해서 다루므로" | 판단의 재료인 실데이터(증상·빈도·비용)를 필수 빈칸으로 강제하되, 초보자가 "정확한 숫자가 없어서" 이탈하지 않게 체감치 입력 경로를 열어둡니다. help의 '대략' 표기 규약이 요구사항 5번의 (추정) 구분·민감도 점검과 맞물리는 입구입니다 — 빈칸과 요구사항이 한 시스템으로 연결됩니다. |
| 요구사항 | "되돌리기 쉬움 2점 이하이면서 정착 리스크 4점 이상인 방안은 전면 도입으로 권고하지 말고, 규모를 줄인 파일럿 실험안으로 바꿔 다시 채점해주세요." | 이 후보의 정체성입니다. '신중하게 판단해달라'는 재량 위임 대신, 판정 임계 규칙 3개(고위험·비가역→실험 강등 / 근거 없는 효과→판정 불가 / 동점→싼 실험 우선)를 요구사항 문장으로 고정합니다. 같은 입력이면 같은 판정이 나오는 재현성이 생기고, 각 규칙에 붙인 이유가 명시하지 않은 유사 상황까지 규칙을 일반화시킵니다. |
| 출력 형식 | "결정 요청 — 무엇을 · 언제까지 · 왜 지금 (문서 최상단) … 확인 필요 목록 — 채점표에 (추정)으로 표기된 항목별로, 누구에게 또는 어떻게 재면 확정치가 되는지" | 결정 요청을 기한과 함께 최상단에 고정해 첫 줄만 읽는 결정권자가 즉시 움직이게 하고(R5 승부처), 미확정 항목은 본문이 아닌 부속 목록으로 분리해 본문은 제출 완성본으로 남깁니다(R10 발송물 정련). 메신저 3줄까지 붙여 보고가 실제로 오가는 두 채널(메신저 선타전 + 문서)에 한 세트로 착지합니다. |

## tips

1. **방안이 없어도 일단 던지세요.** 이 템플릿은 방안을 평가하는 도구이기 이전에 방안을 세우는 도구입니다. 문제 증상·비용·제약만 정확히 넣으면 AI가 제약 안에서 방안을 직접 구성해 같은 채점표에 올립니다. 오히려 어설픈 방안 하나에 이미 꽂힌 상태보다, 문제만 정확한 상태가 더 공정한 판정을 받습니다.
2. **숫자를 모르면 "대략"을 붙여서라도 적으세요.** "취합에 매주 대략 2~3시간" 같은 체감치면 충분합니다 — 채점표가 (추정)으로 구분 표기하고, 민감도 점검이 "그 추정이 절반이어도 결론이 유지되는가"까지 확인해줍니다. 반대로 숫자를 아예 빼면 그 방안은 판정 불가로 빠져 결정이 미뤄집니다. 부정확한 숫자는 시스템이 다뤄주지만, 없는 숫자는 판정 자체를 막습니다.
