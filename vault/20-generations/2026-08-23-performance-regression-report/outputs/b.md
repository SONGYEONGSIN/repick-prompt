- 작성자: 문가은 (성능 엔지니어, 온콜 담당)
- 작성일: 2026-08-23

## 조건 가설별 판정 카드

### 카드 1. 동일 부하 조건(동시접속 150세션·카드 50개)에서의 기본 응답속도 저하

- **조건 가설**: 특정 브라우저·카드 수량·시간대와 무관하게, 기준선과 동일한 부하 조건에서 v3.9.0 배포 이후 응답속도 자체가 저하되었는가.
- **관련 신고 항목(원문 인용)**: 박서연(8/18) — "칸반보드 로딩이 요즘 답답할 정도로 느려요. 예전보다 훨씬 자주 그런 것 같고, 하루에도 몇 번씩 멈칫거려요." (특정 브라우저·카드 수·시간대를 지목하지 않은 일반적 저하 신고)
- **기준선 측정치(원문 인용)**: "8/4(월) 새벽 배치 성능 테스트 — 칸반보드 카드 목록 API, 동시 접속 150세션, 테스트 프로젝트 카드 50개 기준. P95 응답 320ms, P50 응답 140ms. 브라우저 무관(헤드리스 크롬 자동화 테스트)."
- **현재 수치(원문 인용)**: "8/20(목) 오후 2시 재측정 — 기준선과 동일 조건(동시 접속 150세션, 카드 50개)으로 수동 재현: P95 410ms, P50 165ms."
- **(계산)**: P95 320ms → 410ms, 약 28% 증가. P50 140ms → 165ms, 약 18% 증가.
- **참고**: v3.9.0(칸반보드 카드 렌더링 로직 리팩토링)이 8/17(월) 오전 프로덕션 배포됨. 이번 재측정은 그 이후 시점에 이루어짐. 다만 리팩토링 내부 로직이 구체적으로 이 저하를 어떻게 유발했는지에 대한 기술적 원인은 raw 자료에 없으므로 확정하지 않는다.
- **최종 판정**: **회귀 확인** — 기준선과 완전히 동일한 부하 조건(동시접속 150세션, 카드 50개)에서 재현 측정한 결과 P95·P50 모두 뚜렷하게 증가함.

### 카드 2. 브라우저 간 차이(크롬 vs 사파리)로 인한 특정적 저하

- **조건 가설**: 크롬 환경이 사파리 대비 유독 느려진 것인가(브라우저에 특정된 저하).
- **관련 신고 항목(원문 인용)**: 김도현(8/19) — "크롬에서 칸반보드 열면 5초 넘게 걸려요. 근데 사파리에서는 그런대로 괜찮은 것 같아요."
- **기준선 측정치(원문 인용)**: 기준선 자료 없음 — 기준선은 "브라우저 무관(헤드리스 크롬 자동화 테스트)"으로만 진행되어 크롬·사파리를 나눈 비교 수치가 존재하지 않는다.
- **현재 수치(원문 인용)**: "8/20(목) 오후 재측정 — 브라우저 비교, 동시 접속 150세션·카드 50개 동일 조건: 크롬 P95 430ms, 사파리 P95 415ms. 유의미한 차이 없음."
- **참고(격차 미해소)**: 김도현이 보고한 "5초 넘게"(5,000ms 이상)는 동일 조건 재측정치(크롬 430ms)와 큰 차이가 있다. 이 격차의 원인은 raw 자료에 없어 규명되지 않았으며, 원인을 추측해 서술하지 않는다. 크롬 환경 세부사항(확장 프로그램 등)에 대한 CS팀의 추가 확인이 필요할 수 있다.
- **최종 판정**: **회귀 아님** — 동일 조건 재측정에서 크롬과 사파리 간 응답속도에 유의미한 차이가 확인되지 않아, "크롬에 특정된 저하"라는 조건 가설은 뒷받침되지 않는다. (단, 신고된 절대값 자체의 재현성은 별도 확인 사항으로 남는다.)

### 카드 3. 카드 수량 규모(100개 이상 대형 프로젝트)에서의 저하

- **조건 가설**: 카드가 100개를 넘는 대형 프로젝트에서만 저하가 발생하는가(카드 수량 규모에 특정된 저하).
- **관련 신고 항목(원문 인용)**: (주)그린테크(8/19, 세일즈팀 전달) — "카드가 100개 넘는 프로젝트에서만 느려요, 작은 프로젝트는 빠른데 이 프로젝트만 그래요."
- **기준선 측정치(원문 인용)**: 기준선 자료 없음 — 기준선은 "테스트 프로젝트 카드 50개 기준"으로만 측정되어 100개 이상 카드 조건에서의 기준 수치가 존재하지 않는다.
- **현재 수치(원문 인용)**: "8/20(목) 오후 재측정 — 카드 500개 프로젝트, 동시 접속 150세션 동일: P95 1,400ms. (이 카드 수 조건의 기준선 측정치는 없음.)"
- **최종 판정**: **판정불가** — 카드 500개 조건에서 P95 1,400ms라는 현재 수치는 있으나, 대조할 기준선 수치가 없어 이것이 v3.9.0으로 인한 저하인지, 원래부터 대량 카드 환경에서 나타나던 특성인지 구분할 수 없다. 서지호(프론트엔드팀)에게 v3.9.0 카드 렌더링 로직 변경과 카드 수량의 상관관계, 사전 성능 검증 여부 확인 필요(위 확인 요청 목록 참조, 기한: 8/24 회의 시작 전).

### 카드 4. 저녁 시간대(18~20시) 자체 요인에 의한 저하 (부하 통제 시)

- **조건 가설**: 동일한 동시접속 수준을 유지했을 때도 저녁 6~8시라는 시간대 자체가 응답속도 저하를 유발하는가.
- **관련 신고 항목(원문 인용)**: 이하은(8/20) — "저녁 6시에서 8시 사이에 유독 느려요. 낮에는 괜찮은데."
- **기준선 측정치(원문 인용)**: 기준선 자료 없음 — 기준선은 "8/4(월) 새벽" 단일 시점에만 측정되어 오후·저녁 간 시간대별 비교 수치가 존재하지 않는다.
- **현재 수치(원문 인용)**: "8/20(목) 오후 재측정 — 시간대 비교, 동시 접속 150세션으로 통제: 오후 2시 P95 405ms, 저녁 7시 P95 412ms. 유의미한 차이 없음."
- **최종 판정**: **회귀 아님** — 동시접속 수를 동일하게 통제했을 때 오후와 저녁 사이에 유의미한 응답속도 차이가 없어, "저녁 시간대 자체"가 별도의 저하 요인이라는 조건 가설은 뒷받침되지 않는다. (단, 실제 저녁 시간대의 부하 수준 자체가 다른 문제는 카드 5에서 별도로 다룸.)

### 카드 5. 저녁 피크 시간대 실사용 부하(동시 접속 480세션)에서의 저하 규모

- **조건 가설**: 저녁 시간대에 실제로 발생하는 높은 동시접속 부하(카드 4에서 확인된 "시간대 자체" 요인과 별개로, 부하 수준 자체) 조건에서 저하가 기준선 대비 어느 정도인가.
- **관련 신고 항목(원문 인용)**: 이하은(8/20) — "저녁 6시에서 8시 사이에 유독 느려요. 낮에는 괜찮은데." / 박서연(8/18) — "하루에도 몇 번씩 멈칫거려요." (반복적 체감 저하와 시간대별 실사용 부하 편차가 맞물릴 수 있는 항목)
- **기준선 측정치(원문 인용)**: 기준선 자료 없음 — 기준선은 "동시 접속 150세션" 조건에서만 측정되어 480세션 수준의 기준 수치가 존재하지 않는다.
- **현재 수치(원문 인용)**: "8/19(수) 저녁 7시 모니터링: 동시 접속 480세션(이번 주 최고 피크), 카드 목록 API P95 890ms, P50 310ms."
- **관련 맥락(원문 인용, 판정에는 미반영)**: "8/19 인프라팀 슬랙 공유: 저녁 6~8시대 동시 접속 세션이 평시 대비 약 3배로 증가하는 패턴이 최근 2주간 반복 관찰됨 — 마케팅팀 저녁 푸시 알림 캠페인(8/12 시작)과 시기가 일치."
- **최종 판정**: **판정불가** — 480세션 조건에서 P95 890ms라는 현재 수치는 있으나, 이 부하 수준에 대응하는 기준선 수치가 없어 이 값이 v3.9.0 코드 저하, 부하 증가에 따른 정상적 스케일링, 인프라 용량 한계 중 무엇에 기인하는지 구분할 수 없다. 카드 1에서 확인된 150세션 조건의 저하율을 480세션에 단순 대입해 추정하는 것은 근거 없는 외삽이므로 하지 않는다. 강태오(인프라팀)에게 저녁 피크 부하 증가 원인 및 인프라 용량 확인 필요(위 확인 요청 목록 참조, 기한: 8/24 회의 시작 전).
