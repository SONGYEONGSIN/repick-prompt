## 신고 항목별 판정 카드

### 1. 박서연 — "칸반보드 로딩이 요즘 답답할 정도로 느려요. 예전보다 훨씬 자주 그런 것 같고, 하루에도 몇 번씩 멈칫거려요."

- **기준선 수치 인용**: "8/4(월) 새벽 배치 성능 테스트 — 칸반보드 카드 목록 API, 동시 접속 150세션, 테스트 프로젝트 카드 50개 기준. P95 응답 320ms, P50 응답 140ms. 브라우저 무관(헤드리스 크롬 자동화 테스트)."
- **현재 측정치·조건 인용**: "8/20(목) 오후 2시 재측정 — 기준선과 동일 조건(동시 접속 150세션, 카드 50개)으로 수동 재현: P95 410ms, P50 165ms." (참고: "8/17(월) 오전 배포 로그: 칸반보드 카드 렌더링 로직 리팩토링 v3.9.0 프로덕션 배포 완료." / 보조 자료로 "8/19(수) 저녁 7시 모니터링: 동시 접속 480세션(이번 주 최고 피크), 카드 목록 API P95 890ms, P50 310ms"도 있으나, 이는 세션 수 조건(480 vs 150)이 기준선과 달라 직접 대조 대상은 아님.)
- **(계산)**: 동일 조건(150세션·카드 50개) 기준 P95 320ms → 410ms로 +90ms(계산, 약 +28.1%), P50 140ms → 165ms로 +25ms(계산, 약 +17.9%) 증가.
- **측정 방식 차이 참고**: 기준선은 8/4 새벽 배치·헤드리스 크롬 자동화 측정이고, 재측정은 8/20 오후 수동 재현으로, 측정 시간대·방식이 동일하지 않다는 점은 기록해 둠(다만 세션 수·카드 수 조건은 명시적으로 동일하게 맞춰 재현됨).
- **최종 판정**: **회귀 확인** — 기준선과 세션 수·카드 수 조건을 동일하게 맞춘 재현 측정(8/20)에서 P95·P50 모두 기준선보다 뚜렷이 나쁜 수치가 확인됨. v3.9.0 배포(8/17)와 신고 접수 시작(8/18)의 시점도 일치함.

### 2. 김도현 — "크롬에서 칸반보드 열면 5초 넘게 걸려요. 근데 사파리에서는 그런대로 괜찮은 것 같아요."

- **기준선 수치 인용**: "P95 응답 320ms, 브라우저 무관(헤드리스 크롬 자동화 테스트)." — 브라우저별로 나눈 기준선 자료는 없음(기준선 자체가 브라우저 무관 단일 수치).
- **현재 측정치·조건 인용**: "8/20(목) 오후 재측정 — 브라우저 비교, 동시 접속 150세션·카드 50개 동일 조건: 크롬 P95 430ms, 사파리 P95 415ms. 유의미한 차이 없음."
- **(계산)**: 크롬-사파리 P95 차이 15ms(계산) — 신고에서 주장한 "크롬만 5초, 사파리는 괜찮음" 수준의 격차와는 규모가 다름.
- **추가 확인 필요 사항**: 신고된 "5초 넘게"라는 절대 수치는 현재 어떤 측정 조건(매칭 재현 430ms, 8/19 저녁 피크 890ms, 8/20 카드 500개 조건 1,400ms)에서도 재현되지 않음. (추정: 특정 고객 환경의 브라우저 확장 프로그램·네트워크 등 개별 요인일 가능성 — 확인 필요. 이는 확정된 원인이 아니라 추정임.)
- **최종 판정**: **회귀 아님** — 신고에서 지목한 원인(크롬 vs 사파리 차이)을 동일 조건에서 직접 비교한 결과 "유의미한 차이 없음"으로 확인됨. 다만 신고된 5초 이상이라는 절대 수치 자체는 어떤 측정에서도 재현되지 않아, 개별 고객 환경 요인 여부는 별도 확인이 필요함(CS팀 김도현 고객 담당을 통한 브라우저 환경 확인 권장 — 롤백 판단 대상은 아님).

### 3. (주)그린테크 — "카드가 100개 넘는 프로젝트에서만 느려요, 작은 프로젝트는 빠른데 이 프로젝트만 그래요."

- **기준선 수치 인용**: 기준선 자료 없음 — 기준선은 "테스트 프로젝트 카드 50개 기준"으로만 측정되어, 카드 100개 이상 조건에서의 기준선 수치가 존재하지 않음.
- **현재 측정치·조건 인용**: "8/20(목) 오후 재측정 — 카드 500개 프로젝트, 동시 접속 150세션 동일: P95 1,400ms. (이 카드 수 조건의 기준선 측정치는 없음.)"
- **(계산)**: 같은 날 카드 50개 재현치(P95 410ms)와 비교하면 카드 500개 조건은 +990ms(계산) 높음. 다만 이는 "카드 수에 따른 현재 시점의 응답 시간 차이"를 보여줄 뿐, v3.9.0 배포 전에도 카드 500개 조건에서 유사한 수준이었는지 비교할 기준선이 없어 저하 여부를 가릴 수 없음.
- **최종 판정**: **판정 불가** — 신고된 조건(카드 100개 이상)에 해당하는 기준선 측정치가 없어, 현재 측정된 P95 1,400ms가 v3.9.0으로 인한 저하인지, 원래도 카드 수가 많으면 응답 시간이 늘어나는 특성인지 구분할 수 없음. 위 확인 요청 목록의 서지호(프론트엔드팀) 확인 후 재판정 필요.

---

### 4. 이하은 — "저녁 6시에서 8시 사이에 유독 느려요. 낮에는 괜찮은데."

- **기준선 수치 인용**: "8/4(월) 새벽 배치 성능 테스트 ... P95 응답 320ms"(동시 접속 150세션 기준). 다만 기준선 측정은 새벽 시간대에 이루어졌으며, 저녁 시간대를 별도로 측정한 기준선 자료는 없음.
- **현재 측정치·조건 인용**: "8/20(목) 오후 재측정 — 시간대 비교, 동시 접속 150세션으로 통제: 오후 2시 P95 405ms, 저녁 7시 P95 412ms. 유의미한 차이 없음." 추가로 "8/19(수) 저녁 7시 모니터링: 동시 접속 480세션(이번 주 최고 피크), 카드 목록 API P95 890ms, P50 310ms"와 "8/19 인프라팀 슬랙 공유: 저녁 6~8시대 동시 접속 세션이 평시 대비 약 3배로 증가하는 패턴이 최근 2주간 반복 관찰됨 — 마케팅팀 저녁 푸시 알림 캠페인(8/12 시작)과 시기가 일치"가 있음.
- **최종 판정**: **회귀 아님** — 신고에서 지목한 원인(저녁 시간대 자체)을 동일 세션 수(150)로 통제해 비교한 결과 "유의미한 차이 없음"으로 확인되어, 시간대 자체가 독립적인 저하 요인이라는 주장은 뒷받침되지 않음. 실제 저녁 시간대에 체감되는 저하(8/19 저녁 P95 890ms)는 세션 수가 480으로 평시 대비 약 3배 증가한 데 따른 것으로 보이며, 인프라팀은 이 패턴이 마케팅팀 저녁 푸시 알림 캠페인(8/12 시작) 시기와 일치한다고 관찰함. 다만 이는 "시간대가 원인"이라는 신고 내용과는 다른 변수(동시 접속 세션 수)이며, 480세션 수준에서 v3.9.0 배포 전에도 유사한 응답 시간을 보였는지에 대한 기준선 자료는 없음.
