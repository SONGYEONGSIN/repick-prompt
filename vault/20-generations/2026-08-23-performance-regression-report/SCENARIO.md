# SCENARIO — 성능 회귀 보고서 (태스크플로우 칸반보드)

가상 SaaS 협업 툴 "태스크플로우"의 칸반보드 카드 목록 로딩 속도 저하 신고. 아래는 values.json에 채울 모든 사실이다 — 여기 없는 사실은 결과물에 등장하면 창작으로 판정한다.

## 신고 4건 (reporter_reports)

1. (8/18 CS 접수, 고객 박서연 — 스타트업 대표) "칸반보드 로딩이 요즘 답답할 정도로 느려요. 예전보다 훨씬 자주 그런 것 같고, 하루에도 몇 번씩 멈칫거려요." — **특정 조건에 묶이지 않는 일반 체감·빈도 주장.**
2. (8/19 CS 접수, 고객 김도현) "크롬에서 칸반보드 열면 5초 넘게 걸려요. 근데 사파리에서는 그런대로 괜찮은 것 같아요." — 조건: 브라우저(크롬).
3. (8/19 세일즈팀 전달, 고객 (주)그린테크) "카드가 100개 넘는 프로젝트에서만 느려요, 작은 프로젝트는 빠른데 이 프로젝트만 그래요." — 조건: 카드 수(데이터량).
4. (8/20 CS 접수, 고객 이하은) "저녁 6시에서 8시 사이에 유독 느려요. 낮에는 괜찮은데." — 조건: 시간대.

## 기준선 측정치 (baseline_data)

8/4(월) 새벽 배치 성능 테스트 — 칸반보드 카드 목록 API, 동시 접속 150세션, 테스트 프로젝트 카드 50개 기준. **P95 응답 320ms, P50 응답 140ms.** 브라우저 무관(헤드리스 크롬 자동화 테스트).

## 현재 측정치·재측정 시도·배포 이력 (current_evidence) — 7건

1. 8/17(월) 오전 배포 로그: 칸반보드 **카드 렌더링 로직 리팩토링 v3.9.0** 프로덕션 배포 완료.
2. 8/19(수) 저녁 7시 모니터링: 동시 접속 **480세션**(이번 주 최고 피크), 카드 목록 API **P95 890ms**, P50 310ms.
3. 8/20(목) 오후 2시 재측정 — **기준선과 동일 조건**(동시 접속 150세션, 카드 50개)으로 수동 재현: **P95 410ms**, P50 165ms.
4. 8/20(목) 오후 재측정 — **카드 500개** 프로젝트, 동시 접속 150세션 동일: **P95 1,400ms**. (이 카드 수 조건의 기준선 측정치는 없음 — 기준선은 카드 50개 기준.)
5. 8/20(목) 오후 재측정 — 브라우저 비교, 동시 접속 150세션·카드 50개 동일 조건: **크롬 P95 430ms, 사파리 P95 415ms**. 유의미한 차이 없음.
6. 8/20(목) 오후 재측정 — 시간대 비교, 동시 접속 150세션으로 통제: **오후 2시 P95 405ms, 저녁 7시 P95 412ms**. 유의미한 차이 없음(동시 접속 수를 통제하면 시간대 자체는 무관).
7. 8/19 인프라팀 슬랙 공유: 저녁 6~8시대 동시 접속 세션이 평시 대비 약 3배로 증가하는 패턴이 최근 2주간 반복 관찰됨 — 마케팅팀 저녁 푸시 알림 캠페인(8/12 시작)과 시기가 일치.

## 함정 설계 의도

- **측정 조건 비동등 함정 (c 겨냥)**: 항목 2(320ms→890ms, 라벨: 부하 3배 증가 상태)를 그대로 기준선과 비교하면 178% 악화로 보이지만, 항목 3(동일 조건 재측정 320ms→410ms)만이 동등 조건 비교이며 실제 회귀는 약 28%다. **(계산: 410/320 = 약 1.28배, 표시 필요)**
- **기준선 없음 함정**: 항목 4(카드 500개, P95 1400ms)는 그 카드 수 조건의 기준선이 없다 — "회귀 확인"으로 단정하면 안 되고 "기준선 자료 없음"·"판정 불가"로 정직하게 남겨야 한다.
- **조건 소거 함정**: 브라우저(항목 5)·시간대 단독(항목 6)은 유의미한 차이가 없어 "회귀 아님(그 조건 자체는 원인이 아님)"으로 소거돼야 한다. 저녁 시간대 신고(신고 3)는 사실 부하 증가(항목 7, 마케팅 캠페인과 시기 일치)로 설명되는 것이지 시간대 자체가 독립 원인이 아니다.
- **조건으로 환원 안 되는 신고 함정 (a/b 통제쌍 겨냥)**: 신고 1(일반 체감·빈도 주장)은 브라우저·카드수·시간대 어느 조건에도 깔끔히 대응되지 않는다. 신고 항목 단위 판정형(a)은 구조상 자동으로 다루지만, 원인·조건 단위 재구성형(b)은 커버리지 대조표가 이를 잡아내지 못하면 누락될 위험이 있다.

## 부가 정보

- purpose: 백엔드 팀 리드 오하윤이 v3.9.0 롤백 여부와 우선순위를 이번 주 배포 점검 회의에서 결정하는 데 쓰임
- reporter: 문가은, 성능 엔지니어(온콜 담당)
- routing_contacts: 오하윤(백엔드팀 리드) - 롤백 여부 최종 결정 / 서지호(프론트엔드팀) - 카드 렌더링 로직 v3.9.0 변경 배경 확인 / 강태오(인프라팀) - 저녁 시간대 부하 증가 원인 확인 / 김도현 고객 담당(CS팀) - 크롬 환경 세부 정보(확장 프로그램 등) 확인
- decision_deadline: 8/24(월) 오전 배포 점검 회의 시작 전까지

|---|---|
| 신고 1 (일반 체감·빈도) | 조건으로 환원 안 됨 — 독립 카드 또는 명시적 취급 필요. 회귀 확인(항목 3의 실측 회귀 + 항목 7의 부하 증가로 합리적 설명 가능하나, raw에 이를 "신고 1의 원인"이라고 명시한 문장은 없으므로 확정 귀속은 창작) |
