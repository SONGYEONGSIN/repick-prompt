# DOMAIN — 회의 액션아이템 이행 점검 (R59)

Named query 실행 (`vault/40-queries/domain-fit.md`), GENERATE 방향 풀 설계 직전.

## 1. 본질 리스크

이 도메인 결과물이 실패하는 1순위 원인은 **"보고가 없다"는 같은 표면 아래 서로 다른 세 가지 상황을 뭉뚱그리는 것**이다 — (i) 기한이 지났는데 정말 손도 안 댄 진짜 미착수, (ii) 아직 다음 회의(체크 시점)가 오지 않아 판정 대상 자체가 아닌 것, (iii) 진행 중이라고는 들었지만 완료 증빙이 없어 확인이 안 되는 것. training-completion-checklist(R47)·contract-compliance-checklist(R41)가 이미 이 셋을 각각 다른 도메인에서 분리했다. 이 도메인 고유의 **네 번째 리스크**는 backlog가 명시한 것 — 같은 등급("미착수") 안에 단발성 미착수와 **여러 회의째 반복 이월된 미착수**가 섞이면, 후자의 심각도(방치 누적)가 등급 한 줄에 묻혀 보고받는 사람이 "몇 번째 미루는 항목인가"를 다시 원문을 훑어야만 알 수 있다.

## 2. 본질 루프

**"만든 뒤 측정·반복"이 본질이다.** 이 문서 자체가 "지난 회의 vs 지금"의 반복 대조 구조를 전제로 하며(회의 → 액션아이템 → 다음 회의 → 재점검 → 또 다음 회의…), meeting-decision-log(R29)의 팁("다음 회의 전 확인 필요 항목의 답을 이어붙여 갱신")과 동일한 루프가 이 도메인의 정의 자체다. 단일 회의 요약(meeting-summary 시드)과 다른 점은, 이 도메인은 **여러 회의에 걸친 이력**(각 항목이 몇 번째 회의부터 언급됐는지)을 원문으로 받아야 "반복 이월"을 계산할 수 있다는 것 — 실험 문법(지표·판정·후속)이 아니라 **이력 대조 문법**(시점·회차·기한)이 방향 후보에 필수.

## 3. 결과물의 소비 방식

다음 회의 시작 전 또는 회의 도중 **결재선이 아니라 실행 당사자(담당자 본인 + 회의 진행자)가 항목별로 스캔**한다 — "내 항목이 뭐였지", "누가 몇 번째로 미루고 있지"를 3초 안에 짚어야 한다. 결정 요청 상단 고정(v1.5)의 적용 조건(작성자=결정권자)에는 해당하지 않는다 — 이 점검표를 쓰는 사람(회의 진행자·PM)과 실제로 그 항목을 처리할 담당자는 분리된 감사형 도메인이다.

## 4. 유사 라운드 전례

- **meeting-decision-log (R29, v1.27)** — 확인 상태 3분류 + 라우팅. 가장 가까운 전례지만 R29는 "결정"의 확정 여부를, 이번 타깃은 "약속한 일"의 **이행 여부**를 다룬다.
- **inquiry-handoff-memo (R36, v1.57 약속 이행 추적)** — "약속 내용(원문 인용)/시점·화자/기한/현재 처리 상태" 4요소 구조 + 기한 대조 계산("기한 지남"). 이 도메인에 가장 직접 이식 가능한 프레임워크.
- **training-completion-checklist (R47, v1.19+v1.39 결합)** — 과정별 1:1 절 구성, "확인 필요"에 트리거 미도래·검증 실패 사유 세분화. 다만 이번 도메인은 "과정×대상자" N:M이 아니라 "액션아이템 1개당 이력 1줄"이라 절 구성 축은 다를 수 있음.
- **schedule-delay-analysis (R48, v1.44 이월분/자체분 분해)** — 체인형 구간의 누적 지연 분해. 직접 이식은 어렵다(액션아이템은 순서 종속 구간이 아님)지만 "반복해서 누적되는 지연"이라는 문제의식은 이번 타깃의 방향 가설과 통한다.
- **backlog 방향 가설 (R58 정제 질문)** — 등급 체계 안 특히 심각한 하위 유형을 카테고리 확장 없이 태그로 표시할지. 이번 라운드의 통제쌍(a/b)이 정면으로 겨냥.

## 5. 방향 풀 추천 (3개)

이번 라운드는 backlog 방향 가설을 소비하므로 a·b는 자유 설계가 아니라 **통제쌍**(베이스 완전 동일, 심각 하위유형 표시 방식만 다름)으로 고정한다. c만 자유 domain-fit 방향.

- **a = 인밴드 태그형 (통제쌍 1)** — 베이스: 약속 이행 추적(v1.57) 4요소 구조 + 확인 상태 라벨(v1.27, 완료/진행중/미착수/확인필요) + 기한 대조 계산 + **반복 이월 횟수 계산**(원문에서 몇 번째 회의부터 언급됐는지 대조, 3단계 계산 노출: ①기한 경과 여부 ②반복 이월 회차 ③최종 등급 확정) 전부 동일. 차이는 단 하나 — 반복 이월 회차가 임계값(예: 3회 이상 연속) 이상인 "미착수" 항목의 등급 라벨 앞에 "[반복지연]" 같은 인밴드 태그를 붙인다(판정 카테고리 집합 자체는 4개로 불변).
- **b = 무표시형 (통제쌍 2, 순수 통제)** — a와 문자 그대로 동일하되 태그만 없음. 심각도가 같은 조건이 성립해도 동일 등급 라벨만 사용.
- **c = 이력 계층 내장형 (domain-fit 자유 방향)** — 본질 루프(반복 대조)를 정면으로 겨냥: 액션아이템마다 "최초 언급 회의 → 각 회의에서의 상태 이력"을 타임라인으로 노출하는 프레임워크 내장형. 등급은 최종 상태 하나만 판정하되, 그 등급에 이르기까지의 회차별 이력 자체를 구조적으로 드러내 보고받는 사람이 "왜 심각한지"를 태그가 아니라 이력 그 자체로 확인하게 한다 — a/b(태그 유무)와 완전히 다른 해법 축이라 3자 비교 시 태그 메커니즘의 순효과를 가늠하는 대조군 역할도 겸한다.

## 예측 (라운드 종료 후 DECISION.md에서 실제와 대조)

방향 가설의 검증 설계대로면 a가 b를 이겨야 태그 채택이 성립한다. 다만 지금까지의 패턴(R47·R49·R51·R56이 반복적으로 "적어둔 메커니즘"이 아니라 다른 지점에서 갈림)을 고려하면, a·b 승부가 **정말 태그 유무에서만** 갈리는지(다른 confound 없이)가 관건이고, c가 종합 1위를 가져갈 가능성도 열어둔다 — c는 이력 노출이라는 다른 축으로 "심각도를 드러낸다"는 같은 목적을 태그 없이 달성할 수 있어, 만약 c가 이기면 "태그가 아니라 계산·이력 노출 자체가 승부처"라는 v1.53류(계산 노출 축) 해석이 강화된다.
