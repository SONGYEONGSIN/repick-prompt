# S3 — 상향 다리 (설계)

> 2026-08-01 · 스코프 S3 (전체 3단계 중 마지막) · 선행 [[2026-07-25-vault-as-library-source-design|S1]]·[[2026-07-31-reprompt-entrypoint-merge-design|S2]] 완료

## 배경 — 루프의 열린 끝

S1이 볼트를 라이브러리 원본으로 만들고, S2가 그 라이브러리를 제품에 실어 배포했다. **아래로 흐르는 길**(볼트 → 플러그인 → 사용자)은 뚫렸다. 남은 것은 **위로 올라오는 길**이다: 사람이 실제로 무엇을 반복해서 깎는지가 진화 백로그의 타깃이 되는 경로.

S1이 정한 제약은 그대로다 — 로그는 `~/.reprompt/usage.jsonl`(머신 전역)에, **볼트 밖**이다. 다른 레포에서 깎은 것까지 집계돼야 "무엇을 반복하는가"가 보이고, 로그는 지식이 아니라 원료다. 볼트에는 집계된 제안만 올라간다.

적재는 [[2026-07-31-reprompt-entrypoint-merge|S2 Task 4]]에서 이미 끝났다. S3는 **집계 · 반복 감지 · 제안 카드**다.

## 전제 점검 — 지금 입력이 0건이다

`~/.reprompt/usage.jsonl`이 **존재하지 않는다.** `/reprompt`를 한 번도 쓰지 않았기 때문이다.

이건 버그가 아니라 구조다. 진화 루틴은 `prompt-evolve`를 타므로 `initRun`을 거치지 않아 이 로그를 만들지 않는다 — 의도된 설계다(usage 로그가 재려는 것은 "**사람이** 무엇을 반복해 깎는가"이지 자동 라운드가 아니다).

따라서 S3는 **만들어두면 언젠가 도는 기능이 아니다.** 사람이 `/reprompt`를 쓰기 시작해야 비로소 입력이 생긴다. 이 조건을 설계 전제로 명시하고, 아래 단계 분할의 근거로 삼는다.

## 핵심 난제 — 무엇을 "같은 작업"으로 묶나

`task` 문자열은 매번 다르다("콜드 이메일 써줘" / "아웃리치 메일 좀"). `slug`도 따라서 다르다. 안정적인 축은 `target`(4종)뿐인데 너무 거칠다.

**여기서 어제의 교훈이 그대로 적용된다.** [[2026-07-31-reprompt-entrypoint-merge|SCENARIO 사실 누락 검사]]를 만들 때 n-gram 커버리지 휴리스틱을 먼저 설계했다가, 16개 라운드에 실측해보고 나서야 오탐 덩어리임을 알고 폐기했다. 돌려볼 데이터가 있었기에 폐기할 수 있었다.

**지금은 돌려볼 데이터가 0건이다.** 클러스터링 임계를 지금 정하면 검증 불가능한 추측이 된다.

→ 임계를 정하지 않는다. 대신 **클러스터링을 우회하는 신호를 먼저 심는다.**

## 설계 — 클러스터링을 우회한다

현재 로그는 "무엇을 깎았나"만 기록하고 **"라이브러리가 그걸 덮었나"를 기록하지 않는다.** 그런데 S2가 만든 3층 라우팅이 이미 매 실행마다 그 판정을 한다 — 1층(라이브러리 히트)이냐 2층(뼈대 없이 조립)이냐.

**2층으로 내려간 실행 = 라이브러리가 못 덮은 작업**이다. 그것만 모으면 후보 집합이 곧 백로그 후보이고, 유사도 클러스터링 없이도 신호가 깨끗하다.

### 1. 로그 스키마 확장 (S3a)

S2 Task 4가 만든 5필드에 둘을 더한다:

| 필드 | 값 | 왜 |
|---|---|---|
| `layer` | `1` \| `2` | 2층만 모으면 라이브러리 공백이 그대로 드러난다 |
| `matched_slug` | 슬러그 \| `null` | 1층일 때 어떤 템플릿이 쓰였는지 |

**부수 효과가 본 효과만큼 크다** — `matched_slug`가 쌓이면 **라이브러리 적중률**을 잴 수 있다. 31종이 실제 수요를 얼마나 덮는지, 어떤 템플릿이 한 번도 안 쓰이는지가 보인다. 지금은 승격만 하고 사용 여부는 아무도 모른다.

### 2. 집계 스크립트 (S3b)

`scripts/usage-report.mjs` — 로그를 읽어 **원자료를 정리해 보여줄 뿐 판단하지 않는다**:

- 2층 실행 목록 (최근순 / 반복 의심순)
- 1층 적중률과 템플릿별 사용 횟수 (한 번도 안 쓰인 템플릿 포함)
- 기간·건수 요약

유사도 판단을 스크립트에 넣지 않는 이유는 위와 같다 — 튜닝할 데이터가 없다. 묶는 판단은 3층 훅에서 **모델**이 한다(SKILL에 이미 그렇게 적혀 있다).

### 3. 판정과 제안 (S3c)

- **자동 백로그 삽입은 하지 않는다.** `backlog.md`는 자율 루틴이 매일 소비하는 큐다. 잘못된 타깃 하나가 하룻밤 라운드를 통째로 낭비시키고, 그 라운드는 되돌리려면 PR을 닫고 백로그를 손봐야 한다. 제안은 **보고로 끝내고 사람이 넣는다.**
- 제안 카드는 백로그의 기존 타깃 형식(한 줄 + 선정 근거)을 따른다 — 새 형식을 만들지 않는다.
- 이미 라이브러리에 있는 작업은 제안하지 않는다(1층 히트였다면 애초에 목록에 없다).

### 4. 임계는 데이터가 정한다

`N회 반복`의 N을 지금 못 박지 않는다. 로그가 **20~30건** 쌓인 뒤 실제 분포를 보고 정한다. 그 전까지 3층 훅은 지금처럼 "근거가 뚜렷할 때만 언급, 애매하면 침묵"을 유지한다.

## 단계 분할

| 단계 | 내용 | 선행 조건 |
|---|---|---|
| **S3a** | 로그 스키마에 `layer`·`matched_slug` 추가 | 없음 — 지금 가능 |
| **S3b** | 집계 스크립트 + 임계 확정 | 로그 20~30건 축적 |
| **S3c** | 제안 카드 + 3층 훅 임계 반영 | S3b |

**S3a만 지금 한다.** 데이터가 없는 상태에서 S3b·S3c를 설계하면 검증할 수 없는 추측이 되고, 정작 데이터가 쌓였을 때 다시 써야 한다. S3a는 데이터가 필요 없고, **하는 순간부터 S3b가 쓸 신호를 쌓기 시작한다** — 시계를 일찍 돌리는 것이 S2 Task 4에서 적재를 당겨온 것과 같은 이유다.

## 검증

### S3a

1. `layer`·`matched_slug`가 기록되는지 (1층/2층 각각)
2. 기존 5필드가 깨지지 않는지 (S2 Task 4 테스트 전부 통과)
3. **테스트 밀폐** — 기본 경로가 사용자 홈이므로 `usageLog: false` 헬퍼를 계속 쓴다 (S2 Task 4에서 실제로 홈을 오염시킨 적이 있다)
4. SKILL 6단계가 새 필드를 읽도록 갱신

### S3b·S3c (뒤로)

임계 확정 시 **실제 로그 분포에 돌려보고** 정한다. 추측으로 정한 임계는 채택하지 않는다.

## 범위 밖

- **자동 백로그 삽입** — 위 3번 사유
- **다른 레포 로그 수집** — 이미 머신 전역이라 별도 작업이 없다
- **로그 회전·보존 정책** — 한 줄 200바이트 남짓이라 수천 건이어도 문제가 없다. 실제로 커지면 그때 다룬다
- **진화 라운드를 로그에 넣기** — 의도적으로 제외한다. 이 로그는 사람의 반복을 재는 것이고, 자동 라운드는 이미 ledger에 남는다
